# 如何扩展求解器（给下一个人）

> 这份文档解决一个问题：**别人想给这个项目加功能时，知道该动哪里、以及怎么证明自己没改错。**
> 本项目最大的坑不是"不会写代码"，而是"改完不知道结果对不对"——历史上就漏掉过一个把
> 应力放大 1e7 倍的错误（见 `03-修复记录.md` 第五节）。所以本文每条路径都配了验证方式。

---

## 1. 求解器的数据流

`POST /api/solve` 进来后依次做六件事（都在 `backend/solver.py` 的 `solve_simulation`）：

| 步骤 | 做什么 | 关键代码 |
|---|---|---|
| 1 | 校验文件名、查材料 | `resolve_upload_path()`、`MATERIALS_DB` |
| 2 | 读网格 | `load_tet_mesh_from_msh()` → 返回 `(MeshTet, {面tag: 边界三角形})` |
| 3 | 建基函数与刚度阵 | `Basis(mesh, ElementVectorH1(ElementTetP1()))`、`asm(linear_elasticity(lam, mu))` |
| 4 | **施加边界条件** | 定位节点 → 按 `bc.type` 分派 → 写 `f` / `prescribed_dofs` / `warnings` |
| 5 | 求解 | `solve(*condense(K, f, x=prescribed_values, D=D))` |
| 6 | 后处理 | 支反力 `K@u - f`；Von Mises 在积分点求值后 L2 投影到 P1 |

第 4 步是**最常被扩展**的地方；第 6 步是**最容易算错**的地方。

### 1.1 边界条件是怎么"定位节点"的

优先走**精确路径**：`face_triangles[entityIndex]` 是 Gmsh 在 `.msh` 里保留的
「几何面 → 边界三角形」映射，直接给出该面的节点，并按**归属面积**加权
（`nodal_tributary_areas`：线性三角形每个顶点分得面积 1/3，故节点力之和 = 载荷 × 面积）。

拿不到映射时才退化为几何搜索（点到平面距离 → 包围盒启发式），并打 debug 日志。

## 2. 新增一种边界条件类型（完整范例）

以本项目的 `displacement`（强制位移）为例——它原本被求解器**完全忽略**，
用户加了它只会看到"求解成功、结果为零"。下面是当时实际做的四步：

### 第 1 步：模型里必须有承载字段

`backend/constraints.py`：

```python
class BoundaryCondition(BaseModel):
    model_config = ConfigDict(extra="forbid")   # ← 关键：不让字段被静默丢弃
    type: Literal["fixed", "displacement", "force", "pressure", "temperature"]
    displacement: Optional[Union[Vector3, dict, List[float]]] = None
    fixedX: Optional[bool] = None               # 逐分量开关
    fixedY: Optional[bool] = None
    fixedZ: Optional[bool] = None
```

> ⚠️ **这一步最容易漏**。`pressure` 当初就是"`type` 里有、字段里没有"，
> Pydantic 默认 `extra="ignore"` 会把值悄悄扔掉，于是后端永远拿到 0。
> 现在开了 `extra="forbid"`，字段对不上会直接 422。

### 第 2 步：加入支持列表并实现分派

`backend/solver.py`：

```python
supported_types = {"fixed", "displacement", "force", "pressure"}
...
elif bc.type == "displacement":
    values = _parse_displacement(bc)            # dict / Vector3 / list 统一成 (ux,uy,uz)
    flags = (bc.fixedX, bc.fixedY, bc.fixedZ)
    if all(f is None for f in flags):           # 与前端默认值一致：全约束
        flags = (True, True, True)
    for component in (c for c in range(3) if flags[c]):
        for node_idx in target_nodes_indices:
            prescribed_dofs[int(basis_vec.nodal_dofs[component][node_idx])] = float(values[component])
```

**不支持的旧类型不要静默丢掉**——写进 `solver_warnings`，随响应返回，前端会弹黄色横幅。

### 第 3 步：非齐次Dirichlet 要用 `condense(x=...)`

零位移（固定约束）和非零位移（强制位移）**走的是同一套** `prescribed_dofs`，
只是值不同：

```python
prescribed_values = np.zeros(basis_vec.N)
for dof, value in prescribed_dofs.items():
    prescribed_values[dof] = value
u = solve(*condense(K, f, x=prescribed_values, D=D))
```

要点（踩过的坑）：`x` 是**全长向量**，只有 `x[D]` 会被用到；
内部等价于 `b_I - A_ID @ x_D`（见 `skfem.utils.condense` 源码）。
另外 `D` 为空时要保留"自动约束 3 个远端点"的兜底，否则矩阵奇异。

### 第 4 步：前端补齐 UI

- `frontend/components/BoundaryConditionSelector.tsx`：该类型的输入控件；
- `frontend/types.ts`：联合类型；
- 若前端有字段名与后端不一致，**以 `tests/test_solver_regression.py` 的
  `BoundaryConditionContractTest` 为准**——它按前端实际发送的形状构造 5 种边界条件，
  字段漂移会立刻失败。

### 第 5 步（不可省）：加验证

见第 5 节的判据表。强制位移用的是"精确性 + 线性性 + 物理量级"三层断言。

## 3. 新增一种分析类型（例如稳态热传导）

比新增边界条件大，但路径清晰。需要动的地方：

| 位置 | 改动 |
|---|---|
| `backend/materials.py` | 加材料属性（例如热导率 `thermalConductivity`；**记得同时改 `material_store.py` 的表结构与迁移**，否则老库打不开） |
| 新建 `backend/thermal_solver.py`（本项目已落地为 `thermal.py`） | 新的弱形式装配：`asm(laplace(k), basis)`，边界条件改为"给定温度" |
| `backend/main.py` | 挂载新路由 |
| `backend/jobs.py` | 加一个 `POST /api/jobs/<kind>`（长任务必须能异步跑） |
| `backend/fe_utils.py` | 直接复用网格读取与**面→节点定位**，不要另写一套 |
| `frontend/components/SolverSettingsModal.tsx` | `ANALYSIS_TYPES` 里已列出 4 种；把对应项接到新端点，并在底部那段说明里**如实标注**哪些类型后端已实现（否则界面就在"说谎"） |
| `frontend/components/Workbench.tsx` | 求解时按 `solverType` 选端点（`thermal` → `/api/jobs/thermal`，`modal` → `/api/jobs/modal`，其余 → `/api/jobs/solve`） |
| 测试 | 解析解：一维杆两端定温 → 线性温度分布、热流 `q = k·ΔT/L`；模态 → 见 §3.1 |

> 实战经验（来自本项目的热传导实现）：线性单元能**精确重现**线性解，因此
> "两端定温 + 其余面绝热"的一维导热算例可以把容差卡到机器精度（温度 1e-9、
> 热流相对 1e-6）。挑算例时优先找这种"有限元恰好精确"的情形。

### 3.1 第二种扩展方式：模态分析（问题形式变了）

热传导只是换了弱形式，**模态分析（`backend/modal.py`）换的是问题类型**：
从"解 `K u = f`"变成"解 `K φ = λ M φ`"。这条路径上会多出四个只在运行时
才暴露的坑，扩展任何**特征值 / 时间推进**类分析都会遇到：

| 坑 | 现象 | 处理 |
|---|---|---|
| 向量质量矩阵 | `asm(skfem.models.poisson.mass, basis_vec)` 抛 `could not broadcast input array from shape (3,4) into shape (6,)` | `poisson.mass` 是被积函数 `u*v`，**对向量单元不做分量缩并**。自己写 `@BilinearForm def vector_mass(u, v, _): return dot(u, v)` |
| 奇异矩阵上的 shift-invert | 自由-自由（无约束）时 `K` 本来就奇异，`sigma=0` 需要分解 `K` 本身，不可靠 | 用**负** shift：`(K + αM)⁻¹M`，`α>0` 时 `K+αM` 恒正定；`which="LM"` 仍返回最小 λ |
| shift 的取值 | `α` 取太大（`0.1·trace(K)/trace(M)`）会**丢掉一个零模态** | `λ = 1/ν − α` 有相减抵消，α 越小精度越高；但 α 太小又让分解接近奇异。实测 `α = 1e-6·trace(K)/trace(M)` 稳定 |
| ARPACK 的随机初值 | 同一输入两次求解结果不同 | 固定 `v0`（`np.random.default_rng(0).random(n)`）。不可复现 = 不可测试 |

**语义上要主动说明的**：特征值问题是**齐次**的，所以

- 载荷（`force`/`pressure`/`temperature`）**不影响固有频率**，只取"哪些自由度被约束"；
- 用户填的"位移数值"不参与求解。

两条都要进 `warnings`。不说明的话，用户会以为是自己操作错了。

**验收判据的选法（重要）**：路线图原本写的是"悬臂梁一阶频率 vs 解析解误差 <5%"，
实测发现这条标准本身有问题——线性四面体在细长梁弯曲上有**剪切锁死**，
而且参考解要选对模量。改用三条**精确关系**，它们不依赖任何梁理论近似：

| 层次 | 判据 | 实测 |
|---|---|---|
| 刚度矩阵 | 解析刚体模态满足 `K u = 0`（相对残差） | 1e-16 |
| 质量矩阵 | 平移 `uᵀMu = ρV`；转动 `uᵀMu = ρV(w²+h²)/12` | 差 3e-16 |
| 求解器 | 自由-自由**恰好 6 个**零特征值；振型 `φᵀMφ = I` | 零模态/λ₇ ≈ 4e-12；1e-8 |
| 解析频率 | 全域滚动支承细杆 `f_n = (2n−1)/(4L)·√((λ+2μ)/ρ)` | 二阶收敛：6.4e-3 → 4.0e-5（nx=4→32） |
| 单位链路 | 同一网格按 mm/m 解释，频率比**恰好 1000** | 1000.000000000008 |

> **注意 `λ+2μ` 而不是 `E`**：`u_y = u_z = 0` 的滚动支承下材料不能横向收缩，
> 有效模量是**侧限模量** `E(1−ν)/((1+ν)(1−2ν))`，ν=0.3 时比 `E` 大 34.6%
> （频率高 16.0%）。用 `E` 做参考会得到一个**不随网格收敛的 16% 偏差**——
> 这是"参考解错了"的典型特征：**离散误差一定随 h→0 消失，不消失的就是模型假设的差别。**

**"测收敛阶"比"单点容差"强**：与其断言"某个网格上误差 <5%"，不如断言
"网格加密一倍、误差降到约 1/4"。后者同时验证了离散格式的正确性，
而且网格粗糙时的容差不必放宽。

**建议**：先只做"能算对"的最小闭环（一个解析算例 + 一条 API + 测试），
再补 UI。历史上一次性改太多地方，验证不过来就容易被"看起来成功了"骗过去。
（模态分析这一轮就是这么做的：后端 + 34 个解析校验用例先落地并全绿，
前端振型选择界面留到下一轮——`SolverSettingsModal` 底部的说明也如实标明了
"模态已实现但界面未接线"，所以界面**没有**在说谎。）

## 4. 性能与数值上的扩展点

| 想做的事 | 从哪里下手 |
|---|---|
| 更大的网格 | `condense` 换迭代求解器（CG + 预处理），现在用的是稀疏直接法；模态分析的 shift-invert 会做一次稀疏 LU 分解，大模型上这是主要开销 |
| 面载荷 | 现在是"三角形面积 1/3 分给顶点"，**对线性三角形 + 常数面力这是精确解**（`∫N_i dA = A/3`），已用 `FacetBasis` 精确积分对照验证（相对差异 3.7e-16）。若将来改用高阶单元或非均匀面力，则需要改为在面基函数上组装真实面载荷向量 |
| 单元阶次 | `ElementTetP1` → `ElementTetP2`（同时要改网格读取里的单元类型映射，现在只识别 gmsh 的 4 节点四面体）。**模态分析最需要它**：线性四面体在弯曲问题上偏刚 |
| 非线性 / 动力学 | 需要引入时间步或牛顿迭代；建议先把 `solve_simulation` 拆成"装配 / 施加 / 求解 / 后处理"四个函数再动 |
| 更多模态 / 更大模型 | `eigsh` 求的模态数受可用自由度数限制（`k < N_free`）；`modal.py` 里已有截断与 `ArpackNoConvergence` 的部分结果处理 |
| 长任务 | 网格与求解已改为 `/api/jobs/*` 异步任务（提交→轮询）。新增耗时分析类型时**务必走同一条路** |

## 6. 已知陷阱清单

| 陷阱 | 说明 |
|---|---|
| gmsh 线程约束 | `gmsh.initialize()` / `finalize()` 会调用 `signal.signal()`，而**信号处理只能在主线程设置**。因此不能在工作线程里 initialize/finalize。本项目由 `gmsh_session.py` 在主线程初始化一次、进程内复用，每次操作前 `gmsh.clear()`；所有 gmsh 操作都在 `jobs.py` 的单线程工作器里排队 |
| SQLite 连接 | `with sqlite3.connect(...) as conn` **只提交事务、不关闭连接**，用在循环里会泄漏句柄并锁住数据库文件（Windows 上连删除都失败）。用 `material_store._cursor()` 那种写法：`try: with connection: yield ... finally: connection.close()` |
| Pydantic 静默丢字段 | 默认 `extra="ignore"`。新增字段一定要同时改模型，本项目已开 `extra="forbid"` |
| `eye(w, n)` 的语义 | 它**把 w 放到对角线**，所以偏应力是 `s - (1/3)*eye(trace(s), 3)`，**不要再乘一次 trace**（乘了就是 tr²，应力会大出几个数量级） |
| NumPy 2 的 `np.cross` | 轴约定改成了**末轴**；`(3, N)` 形状必须转置成 `(N, 3)` |
| skfem 版本差异 | 12.x 里 `Basis.project()` 不接受 `Functional`；`Mesh.load()` 依赖 meshio（本项目改用 Gmsh 直接读） |
| gmsh 单位 | 坐标来自 CAD，**通常是毫米**。现在由 `length_unit` 显式声明并在求解前换算成米，结果一律 SI（位移 m、应力 Pa）。新增涉及长度量纲的代码时，请确认它用的是**换算后**的坐标（`mesh.p`），面元数据里的 `center` 仍是**输入单位**，需要乘 `length_scale` |
| 绝对容差 | 单位换算会暴露所有写死的容差：原先"点到平面距离 < 1e-2"在毫米模型上会把整个模型选进来。现在一律用**相对模型尺度**（`model_span * 1e-3`） |
| Windows 控制台编码 | GBK 代码页下打印 emoji 会抛 `UnicodeEncodeError`；任务脚本已设 `errors="replace"`，新代码请避免 emoji |
| PowerShell 读写 UTF-8 源文件 | `Get-Content` 在 Windows PowerShell 5.1 下**默认按 ANSI 解码**。对无 BOM 的 UTF-8 源文件用 `Get-Content ... \| Set-Content -Encoding UTF8` 会把中文**二次编码**成乱码（本项目真踩过，靠 git 恢复）。改文件请用编辑工具，或显式 `Get-Content -Encoding UTF8` |
| `.ps1` 需要 BOM | 无 BOM 的 UTF-8 会让 PowerShell 5.1 按 ANSI 解析中文而语法报错（`.editorconfig` 已声明） |
| `python` 可能是 Store 桩 | Windows 上 `python` 常是"应用执行别名"，调用无输出也不报错；用 `py -3` 或 venv 里的解释器 |
| **测试里别留下后台任务** | gmsh 状态是进程级全局的，本项目约定所有 gmsh 操作都在 `jobs.py` 的单线程工作器里串行。若某个测试中途断言失败、把任务留在工作线程继续跑 gmsh，而下一个测试又在主线程调用 `gmsh.open`，两边并发访问同一份全局状态 ⇒ `OSError: access violation reading 0x0`（**与真实失败原因毫无关系**，报错位置看起来像 gmsh 坏了）。写法：先轮询到任务终态再断言，并在 `tearDown` 里排空队列（见 `test_modal._drain_job_queue`） |
| **"声明了但从未被读取"的数据通路** | 本轮最严重的缺陷：着色器里 `uniform float deformationScale` 存在、CPU 侧每帧都在算并写入它、`max_displacement` 也一直在传，**唯独 GLSL 里没人读它** ⇒ 云图永远画未变形几何。不报错、不影响数值、`tsc`/`build` 全绿。加渲染/显示相关的代码时，请反向核对"这个值在最终消费点被读了吗" |
| **写死的"绝对"显示参数** | `targetVisualDisp = 0.5` 这种常量在毫米级 CAD 零件上等于不显示变形、在 1 单位模型上又夸张到 50%。**凡是与模型尺寸相关的显示参数都必须是相对量**（本项目取"模型最大尺度的 8%"），并在界面上标注实际倍数 |
| skfem 的 `C_CONTIGUOUS` 噪声 | `np.vstack(cells).T` 之类的转置结果是 F-order，skfem 按维度切片需要 C-order，会对 >1000 单元的网格打印 `Transforming over N elements to C_CONTIGUOUS`。它只是噪声，但会淹没真警告——`fe_utils.load_tet_mesh_from_msh` 已用 `np.ascontiguousarray` 处理 |
| **Python 循环变量会泄漏** | `for index, node in enumerate(cube["nodes"])` 之后，`node` **仍然是**最后一个节点坐标数组。在同一个函数里再用 `node` 表示别的含义（例如 Node.js 可执行文件路径）就会拿到一个数组，最后以 `TypeError: expected str, bytes or os.PathLike object, not list` 的形式在完全无关的地方炸掉。**别给"环境/工具类"变量起与业务数据同名的名字**（本项目的 `task_verify` 里已统一叫 `node_bin`） |
| 兜底 `except` 吞掉调用栈 | 大段的端到端校验常包在一个 `except Exception` 里转成"一项失败"，但只报一行异常摘要的话根本定位不到行号。本项目已在 `task_verify` 的兜底捕获里加 `traceback.print_exc()`——就是靠它才查出上一条那个循环变量覆盖问题 |
| 显示的"缺失值"被当成"零" | `Number(null)`、`Number('')`、`Number(false)` **全都等于 0**。频率格式化函数第一版就因此把"数据缺失"显示成 `0 Hz`，而在模态界面里 `0 Hz` 的含义是"刚体模态"。格式化/解析用户可见数值时，**必须在 `Number()` 之前**排掉 `null/undefined/''/布尔`，并把入参声明为 `unknown`（数据来自 JSON，本来就不可信） |
| **类型声明与接口数据不一致** | `types.ts` 里 `Project.createdAt` 声明为 `Date`，`tsc` 全绿——但后端返回的是 **ISO 字符串**，旧代码 `proj.createdAt.toLocaleDateString()` 接上真实 HTTP 就抛 `TypeError`。**声明是开发者自己写的，不是从接口生成的**，所以类型检查永远发现不了这类问题。修法是让解析集中在一个边界上（`utils/projectsApi.ts` 的 `toProject`），并写一条显式断言：`typeof '2026-…'.toLocaleDateString === 'undefined'` |
| **PowerShell 5.1 的 `Invoke-RestMethod` 编码** | 发 body 时按 ANSI 编码 ⇒ 中文变 `?`；解析 JSON 响应时按 ISO-8859-1 解码 ⇒ 中文变 `éå¯...`。两条都只发生在**客户端**，服务器与数据库里是正确的 UTF-8。断言编码相关行为必须用能显式控制编码的客户端（`urllib` + `encode/decode('utf-8')`）或浏览器 |
| 新增持久化实体时的 SQLite 细节 | **继承 `sqlite_store.SqliteStore`**，不要重写连接管理：`with sqlite3.connect(...) as conn` 只提交事务、**不关闭连接**，会泄漏句柄并在 Windows 上锁住数据库文件（项目曾因此 14 个 tearDown 失败）。新表只需声明 `table` / `schema` / `migrations` 三件事 |
| **"自动改变归属/权限"的逻辑** | 本项目真踩过：初版写"第一个注册的用户自动接管所有无主项目"，结果 `tools/tasks.py verify` 的固定测试账号成了第一个用户，把开发者手工建的项目**静默划给了测试账号**（用户下次登录就发现项目不见了）。凡是"为了体验而自动改变归属/权限"的逻辑，先问一句：**"如果这段逻辑被一个非人类账号触发，会发生什么？"** 宁可"看得见但要手点一下"（显式认领），也不要静默改归属 |
| **不要把"用户不存在"与"口令错误"分开报** | 分开报等于免费提供一个用户名枚举接口。两者应返回同一句 401，并且耗时接近（用户不存在时也陪跑一次假哈希） |
| **口令/令牌的存储格式要能自描述** | 哈希参数（`n/r/p`）必须写进存储串（`scrypt$n$r$p$salt$hash`），否则改一次参数就等于让所有老用户登不上；令牌则**只存哈希**（数据库被读走也拿不到可用令牌）。另外哈希串来自数据库，属于不可信输入：参数要校验上限，畸形值不能让服务端分配巨量内存 |
| **查询接口别提供"不过滤"模式** | `list_projects(owner_id)` 把属主做成**必填参数**、且没有"返回全部"这个模式。若把 `None` 解释成"不过滤"，任何一处忘记传参的调用都会静默地把所有用户的数据混在一起——而这正是用户隔离要防的事 |
| **给整个 router 加认证，别逐个端点加参数** | `APIRouter(dependencies=[Depends(require_user)])` 一句覆盖全部端点，以后新增端点自动受保护。逐个端点加 `user: dict = Depends(...)` 有代价：端点其实不需要知道"你是谁"，而且**大量测试是直接调用端点函数的**（不经 HTTP），加必填参数会让它们全部失效 |
| **`Path.write_text()` 在 Windows 上会写 CRLF** | 默认做换行转换，把 `\n` 写成 `\r\n`。`.gitattributes` 的 `eol=lf` 会让提交内容正确并给出警告，但工作区与仓库不一致会产生 `git status` 显示 M 而 `git diff` 为空的怪象（索引 stat 缓存过期，`git add` 刷新即可）。用脚本改文件时显式指定 `newline="\n"`，或改完统一规范化 |
| **配置类文档的校验要分级** | 后端自己会消费的字段（文件名、边界条件）从严；纯前端 UI 状态（网格/求解设置）只要求是 JSON 对象 + 总量上限。在 UI 状态上逐字段校验会把后端与前端耦合起来——每改一次界面都要同时改后端 |
| **`model_dump()` 会把文档"充气"** | Pydantic 会把所有未填的可选字段补成 `None` 一起存（实测 17 个字段里 11 个是 null）。存配置/快照类文档时用 `exclude_none=True`；另外注意**响应**经过响应模型序列化时那些 null 会回来——那是模型在起作用，不是数据被改，断言要比"值"而不是比字节 |
| **这个仓库不要用 `git add -A` / `git add .`** | `backend/uploads/` 下有刻意不纳入版本控制的用户文件（如 `零件1.STEP`），`-A` 会把未跟踪文件一起加进来。提交时一律**列明文件名**，并在 commit 前断言"没有 uploads/ 下的文件被暂存" |

## 8. 改了前端怎么验证（没有浏览器时）

仿真项目的最终输出是**画在屏幕上**的，而"界面在说谎"这类缺陷既不属于静态层、
也不属于接口层——接口返回的数值完全正确，只是没人把它画出来。本项目遇到过两次：
选了 `Heat Transfer` 却仍走结构求解；云图着色器不显示变形。

三种可落地做法（都在 `tools/tasks.py verify` 里跑）：

1. **把"UI 实际会发出的请求"写成端到端检查**：按界面代码的形状构造请求体
   （同样的字段名、单位换算、异步轮询路径），断言物理结果。
   前端字段改名会让它立刻失败——这就是 `verify` 里的"热分析前端契约"与
   "模态分析"检查。
2. **把纯计算抽成不依赖框架的模块，用 node 直接执行并断言**。
   Node ≥ 23 支持类型擦除，可以 `import './deformation.ts'`。
   这样前端算法**不必在 Python 里重写一遍**——重写一遍等于测试了一个"副本"。
   例：断言"放大后的相对幅度恒等于目标比例"（跨模型尺寸 10/100/1000、
   位移量级 1e-7~0.5 都成立）、退化输入返回 1 而不是 `NaN`。
3. **对渲染管线做契约检查**：把 GLSL 抽成独立模块（`components/resultShader.ts`），
   检查关键赋值是否真的用上了该用的数据。**注意先剥掉注释**——文档注释里
   常常故意保留了出错前的反例片段，第一版检查就匹配到注释里的
   `vec3 deformedPosition = position;` 而误报。
4. **把后端真实响应喂给前端纯函数**（比造假数据强得多）。
   做法：`verify` 里把接口返回的 JSON 写到临时文件，node 脚本读它再调前端的
   解析/取场函数。例：模态结果 → `modeDisplayField(mode_shapes, 0, nodes.length)`，
   断言"每阶振型长度 == 网格节点数、默认阶次能取场、归一化后最大位移 == 1"。
   它专门挡**字段名漂移**：后端把 `mode_shapes` 改名后，界面只会静默地不显示
   振型——不报错、不影响数值、`tsc` 与 build 全绿。
5. **确认 Vite 真的能编译**新增模块（`tsc` 通过不代表运行时模块解析正确）：
   开发服务器在跑时，直接 `GET http://localhost:3000/utils/你的模块.ts`，
   返回 200 且是转译后的 JS 才算过。
6. **改了"能存数据"的功能，就必须真的重启一次进程再验证**。
   项目持久化那一轮的核心承诺是"项目不会丢"，所以验证是：
   `POST /api/projects` → `tools/tasks.py stop` → `dev --detach` → 按 ID 取回，
   **并直接读 SQLite 确认落盘**。只断言"接口返回了 201"证明不了任何事。
7. **接口形状变了就顺手加一条"数据映射"断言**。后端的 `createdAt` 是字符串、
   前端 `Project.createdAt` 是 `Date`，中间的转换写错会让整个列表崩在渲染里
   （见陷阱清单里的"类型声明与接口数据不一致"）。把映射写成纯函数放在
   `frontend/utils/`，就能用 node 直接断言。
