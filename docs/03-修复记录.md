### 4.3 求解器物理校准（关键）

**算例**：`default_cube.step`（10×10×10 立方体），材料结构钢 E=2×10¹¹ Pa、ν=0.3，一端面全约束、对端面施加 1000 N 轴向拉力。

| 指标 | 解析/期望 | 计算结果 | 判定 |
|---|---|---|---|
| 加载面中心轴向位移 | `FL/AE = 5.0e-10` | `4.17e-10` | 比值 **0.835** —— 全约束端抑制泊松收缩使结构略刚于自由杆，**符合力学预期** ✅ |
| 横向位移 | 量级 ~1e-11 | `uy=-1.16e-11, uz=3.5e-12` | 比轴向小一个数量级，符合泊松效应 ✅ |
| 支反力合力 | 与施加 1000 N 精确抵消 | `Z = -1000.000`（施加 +1000） | **全局平衡严格成立** ✅ |
| 应力场 | 有限、无 NaN | max 614.6 Pa，NaN 数 0 | 无奇异 ✅ |

**⚠️ 一次误判的复盘（值得记录）**：第一次校准时使用了 `face 1` / `face 6`，误以为它们是 ±X 面，得到位移是解析解 3.38 倍的结果，一度怀疑刚度矩阵有问题。后来打印立方体的真实面法向才发现 **`face 6` 实际是 +Z 面**，等于在"端面固定 + 侧面拉伸"的剪切工况下和拉伸解析解对比，属于**测试用例本身的错误**，不是求解器缺陷。按真实法线选面后立即吻合。

> 教训：**校准失败时，先怀疑测试用例，再怀疑代码**；而判断"是哪个错了"的唯一办法是把中间量打出来看（面法向、支反力、位移分量）。

### 4.4 端到端

## 五、第二轮：工程化与物理正确性

第二轮的目标从「能跑」转向「能协作、结果可信」。最有价值的产出是**发现并修复了一个严重的物理后处理错误**。

### 5.1 🔴 Von Mises 应力被放大数个数量级（严重）

| 项 | 内容 |
|---|---|
| **现象** | 10×10×10 立方体施加 1e7 Pa 均布压力（名义应力 1e7 Pa）时，全部 458 个节点的 Von Mises 都在 **1e13~1e14 Pa**——比名义值大 7 个数量级；而位移（5e-4，与解析解 pL/E 吻合）与支反力（精确 1e9 N）却完全正确 |
| **根因** | 偏应力写成了 `s - (1/3)·trace(s)·eye(trace(s), 3)`。`eye(w, n)` 的定义就是**把 w 放到对角线上**，再乘一遍 `trace(s)` 等于把迹平方——对角项变成 tr²，静水应力越大误差越大 |
| **修复** | `s_dev = s - (1/3)·eye(trace(s), 3)`（与 scikit-fem 自身 `linear_stress` 的写法一致） |
| **为何之前没发现** | 早先的验证只断言了「应力有限、无 NaN」。位移与支反力都对，只看这两项根本发现不了应力错了 |
| **现在的防线** | 新增 `VonMisesAnalyticTest`：构造解析位移场 `u_x = εx`（应变 `diag(ε,0,0)`），其 Von Mises 有闭式解 `2με`，按 **1e-6 相对容差**比对积分点值与投影后的节点值，并附一条「不得被放大」的反向断言 |
| **修复后可见效果** | 带孔方块拉伸工况 `max_stress` 从 **4169 Pa → 47.97 Pa**（名义 10 Pa，约 4.8 倍，正是孔边应力集中的合理量级）；`FL/AE` 比值同时从 0.835 改善到 **0.953** |

### 5.2 🟠 `pressure` 边界条件被求解器完全忽略

前端与 AI 助手都能添加「压力」边界条件，但求解器分支只处理 `fixed` 和 `force`——压力既不报错也不产生载荷，用户拿到的是「零载荷却显示求解成功」。

更进一步：`BoundaryCondition` 模型里**根本没有 `pressure` 字段**（`type` 联合类型中有 `"pressure"`，但没有承载载荷值的字段），Pydantic 默认静默丢弃未知字段，所以即便实现了施加逻辑也取不到值。

| 项 | 内容 |
|---|---|
| **修复** | ① 补齐模型字段 `pressure` / `temperature` / `fixedX,Y,Z` / `color`；② 施加真实面载荷 `traction = -p·n`（正压力指向实体内部）；③ 开启 `extra="forbid"`——今后字段对不上会**返回 422 而不是静默丢值** |
| **测试** | 均布压力算例断言：支反力合力 = `p×A`（容差 1e-3）、位移方向为受压、`|δ| ≈ pL/E`、中部应力与 p 同量级 |

### 5.3 🟠 边界条件定位从「几何猜测」升级为「精确映射」

原先靠「点到平面距离」找节点（曲面直接退化成 `entityIndex % 6` 的包围盒猜测）。现在直接从 `.msh` 读取 Gmsh 保留的**几何实体 → 边界三角形**对应关系，精确取到该面节点，**不依赖 Physical Groups 也能达到同等效果**。

同时把载荷分配从「总力 ÷ 节点数」改为**按归属面积加权**（线性三角形每个节点分得所在三角形面积的 1/3），节点力之和精确等于 `载荷 × 面积`。

## 六、第三轮：补齐最后一种边界条件 + 扩展指南

### 6.1 🟠 `displacement`（强制位移）被求解器完全忽略

与 `pressure` 同一类问题：前端 `BoundaryConditionSelector` 提供 5 种边界条件，
而求解器只处理 `fixed` / `force`（后来补了 `pressure`）。
`displacement` 既不报错也不产生约束——用户选了它，得到的是一份**没有该约束**的结果。

| 项 | 内容 |
|---|---|
| **修复** | ① 按 `fixedX/fixedY/fixedZ` **逐分量**约束，值取自 `displacement`（dict / Vector3 / list 均可，统一由 `_parse_displacement` 解析）；② 零位移与非零位移统一走 `prescribed_dofs`，用 skfem 的**非齐次 Dirichlet**：`solve(*condense(K, f, x=prescribed_values, D=D))`；③ 三个方向都没勾选时给出警告而不是静默无操作 |
| **关键细节** | `condense` 的 `x` 是**全长向量**，只有 `x[D]` 参与计算（等价于 `b_I − A_ID·x_D`）；`D` 为空时保留原有"自动约束 3 个远端点"的兜底 |
| **验证（三层）** | ① 精确性：加载面节点的 `ux` 必须**精确等于**给定值（实测误差 **0**）；② 线性性：位移翻倍 ⇒ 支反力精确翻倍（相对误差 < 1e-6）；③ 物理量级：加载面总轴力 / `EAδ/L` = **1.041**（全约束端让短粗立方体略刚，符合预期） |
| **测试用例** | `DisplacementBoundaryConditionTest`（7 个）+ `DisplacementParsingTest`（4 个，覆盖 dict/list/缺省/部分字段） |

## 七、第四轮：单位制 + 工具健壮性

### 7.1 🟠 坐标被当成米用，结果差好几个数量级

CAD 导出的几何几乎都是毫米，但求解器把坐标**直接当米**：一个「10 单位见方」的零件
被算成 10 米，1000 N 载荷得到 **10 Pa**——数值上毫无意义，而用户看到的图例却写着 Pa。

| 项 | 内容 |
|---|---|
| **修复** | `SolverRequest` 新增 `length_unit`（`"m"` / `"mm"`）；求解前把坐标**换算成米**，于是材料 E（Pa）、载荷（N）与结果（m / Pa）全部落在 SI 上。响应新增 `units` 与 `length_unit` 字段，明确声明返回单位 |
| **默认值取舍** | API 默认 `"m"`（SI，**不静默改变既有调用方**）；前端默认 `"mm"`（CAD 习惯），并在「Analysis Type」弹窗里给了一个可见的切换控件与说明 |
| **连带修复** | 两处**绝对容差**改成相对模型尺度：① 面元数据来自原几何（输入单位），需按同一比例缩放后才能与已换算的网格坐标比较；② 点到平面的容差原先写死 `1e-2`，在毫米模型上会大到把整个模型都选进来 |
| **验证** | 同一份网格分别按 m / mm 求解：**应力比 = 1000²、位移比 = 1000，误差 < 1e-6**；按 mm 解释时应力落在 10 MPa 真实量级；非法单位（`inch`）返回 400；默认值与显式 `"m"` 结果逐位一致 |
| **端到端** | `tools/tasks.py verify` 新增两项检查：`mm vs m 应力 ×1000²`、`结果单位声明为 SI` |

### 7.2 🟠 `stop` 停不干净，导致 verify 被"旧代码"服务

本轮 `verify` 出现两项莫名失败（响应里缺 `length_unit`）。排查发现：
**一个更早启动的后端进程仍占着 :8000**，而 `.dev-pids.json` 指向的是后来一次
`dev --detach` 启动、因端口被占而**绑定失败**的进程——于是 `stop` 杀了"没在监听的
那个"，真正的服务活了下来，验证自然测的是旧代码。这类"看起来通过了但测的不是当前代码"
的陷阱，比直接报错更危险。

| 项 | 内容 |
|---|---|
| **根因** | ① `stop` 只信任 PID 文件；② Windows 上 `python -m uvicorn` 会出现**启动器 + 实际监听**两个 python 进程，杀掉其中一个，另一个仍持有监听套接字 |
| **修复** | ① `stop` 增加**按端口兜底**（Windows 用 `netstat -ano`，POSIX 用 `lsof`），并且**反复"查—杀"直到端口真正释放**；② 端口仍被占用时返回非 0 并提示手动处理；③ `dev --detach` 启动前检查端口，被占用时明确警告"否则会写入错误的 PID" |
| **验证** | 故意删掉 `.dev-pids.json` 模拟陈旧进程场景：`stop` 仍能找出并结束两个占用进程，3000/8000 全部释放、exit 0 |

## 八、第五轮：材料持久化 + 更正一处错误的文档结论

### 8.1 🟠 自定义材料重启即丢

材料库原本是一个内存 Python 列表：用户建的自定义材料**一重启就没了**，多人共用
一台机器时还会互相覆盖。这让"长期使用"和"协作"都无从谈起——每个人都要重新录一遍。

| 项 | 内容 |
|---|---|
| **修复** | 新增 `material_store.py`（**标准库 sqlite3，不引入新依赖**）：内置材料始终来自代码（数据库坏了也仍可用），自定义材料写进 SQLite。数据库默认 `backend/data/simcloud.db`（已 gitignore），可用 `SIMCLOUD_DB` 覆盖——测试就靠它使用临时库，不污染开发数据 |
| **接口不变** | `GET/POST /api/materials` 的请求与响应形状完全不变，前端无需改动；新增语义：内置材料 ID 不允许被覆盖（400），重复自定义 ID 返回 400 |
| **为什么用 SQLite 而不是 JSON** | 并发写入更安全，主键约束天然防重复 ID |
| **验证** | 新增 `test_material_store.py`（17 个用例，含"换一个 store 实例模拟重启后数据仍在"）；**端到端实测**：新建材料 → `stop` + `dev --detach` 完整重启后端 → 材料仍在（5 → 6），按 ID 也能查到 |

**过程中修掉的一个真 bug**：`with sqlite3.connect(...) as conn` 是常见坑——连接对象
作为上下文管理器**只提交/回滚事务，不会关闭连接**。最初这样写导致每次调用泄漏一个
句柄，在 Windows 上会一直锁住数据库文件（14 个测试的 tearDown 全部失败）。
已改为显式的 `_cursor()` 上下文管理器：`try: with connection: yield ... finally: connection.close()`。

### 8.2 🟡 更正：面载荷分配其实**不是**"一阶近似"

先前我在 `docs/01`、`docs/04`、`docs/03` 里把"按三角形面积 1/3 分给顶点"写成
「集中式、一阶精度，应改为面基函数积分」。本轮实际验证后发现**这个结论是错的**：

对**线性三角形 + 常数面力**，`∫N_i dA = A/3` 解析成立，因此集中式分配与在
`FacetBasis` 上组装的精确载荷**逐节点完全相同**——实测相对差异 **3.65e-16**（机器精度），
合力也都精确等于 `t·A = 1e9`。

已把三处文档改成正确结论，并新增 `ConsistentTractionTest` 把它固化：
面面积精确、集中式与精确积分一致（相对差 < 1e-12）、合力 = 面力 × 面积。

> 教训与上一轮的 Von Mises 事件一致：**"看起来像近似"不等于"真是近似"，
> 写进文档的结论也要有验证支撑。** 现在这条结论有了可复现的数值证据。

## 九、第六轮：长任务异步化（+ 一个 gmsh 硬约束）

### 9.1 🟠 网格划分/求解同步阻塞 HTTP，大模型必然超时

网格划分与求解是 CPU 密集且耗时不确定的操作，此前都在 HTTP 请求里同步执行：
大模型会让请求超时，浏览器或网关先断开，用户拿到 502 —— 而任务其实还在算。
更糟的是，异步端点直接在事件循环里跑 gmsh，**整个服务在计算期间无响应**。

| 项 | 内容 |
|---|---|
| **修复** | 新增 `backend/jobs.py`：异步任务接口 `/api/jobs/*`（提交立即返回 `job_id`，轮询状态与结果）；同时把**原同步端点也排进同一条队列**，实现只写一份 |
| **为什么单线程** | gmsh 的 Python API 背后是进程级全局状态（当前模型/选项/网格），**不是线程安全的**。让所有 gmsh 操作在同一个工作线程里排队，既天然串行（不会被并发破坏），又不必在业务代码里到处加锁 |
| **事件循环不再被占用** | 同步端点现在是"排进队列 + `await` 结果"，因此计算期间服务仍能响应其它请求（包括轮询任务状态） |
| **前端** | `Workbench` 改为提交 + 每 700ms 轮询，Job status 显示"排队中…/计算中…"，上限 15 分钟 |
| **已知限制** | 任务表在进程内，**服务重启即丢**。生产级方案要外部队列（Redis/RQ），但会显著提高部署门槛，现阶段不值得——已写进 README 的限制表 |

### 9.2 🔴 顺带发现：gmsh 的 initialize/finalize **只能主线程调用**

第一版实现把 gmsh 工作全部放进工作线程后，测试立刻炸出一片：

```
ValueError: signal only works in main thread of the main interpreter
  gmsh.py:295 in initialize -> signal.signal(signal.SIGINT, signal.SIG_DFL)
```

查 `gmsh.py` 源码确认：**只有 `initialize()` 与 `finalize()` 会碰信号处理器**
（L295 / L326），其余所有模型操作都不碰；而信号处理器只能在主线程设置。

| 项 | 内容 |
|---|---|
| **修复** | 新增 `backend/gmsh_session.py`：在**主线程**（模块导入时）初始化一次，进程内复用会话；每次操作前 `gmsh.clear()` 重置，不再 initialize/finalize。所有 `finalize()` 调用（含错误路径）都已移除 |
| **顺带修掉一个潜在缺陷** | 以前依赖"每个请求一次 initialize"来获得干净状态；gmsh 一旦被复用，模型就会**不断累积**。现在统一由 `start_model()` 显式清理 |
| **验证** | 102 个测试全部通过；`verify` 端到端确认异步任务结果与同步接口**逐位一致** |

> 这一条很典型：**"把 gmsh 放到线程里"看起来是纯粹的工程改动，实际撞上了一个
> 库层面的隐藏约束**。如果不是真的跑测试，就会写出一个"编译通过、一跑就炸"的实现。

## 十二、第九轮：模态分析（第三个分析类型）

### 12.1 ✅ 新增模态分析 `backend/modal.py`

无阻尼自由振动 `M ü + K u = 0`，令 `u = φ e^{iωt}` 得到广义特征值问题
`K φ = λ M φ`（`λ = ω²`）。新增 `POST /api/modal/solve` 与
`POST /api/jobs/modal`。

三个**只在运行时才会暴露**的实现细节：

| 问题 | 现象 | 处理 |
|---|---|---|
| **向量质量矩阵** | `asm(skfem.models.poisson.mass, basis_vec)` 抛 `could not broadcast input array from shape (3,4) into shape (6,)` | `poisson.mass` 是被积函数 `u*v`，对 `ElementVectorH1` 的 `(3, n_qp, n_elem)` 插值**不做分量缩并**。向量单元必须自己写 `@BilinearForm def vector_mass(u,v,_): return dot(u,v)` |
| **K 奇异时不能 `sigma=0`** | 自由-自由结构的 `K` 本来就奇异（刚体模态 = 它的零空间），`sigma=0` 的 shift-invert 需要分解 `K` 本身，不保证可用 | 改用**负** shift `σ = -α`（`α = trace(K)/trace(M)·1e-6`）：分解对象 `K+αM` 对任意 `α>0` 恒正定；`which="LM"` 作用在 `(K+αM)⁻¹M` 上仍返回最小 λ |
| **shift 不能取大** | `α = 0.1·trace 比值` 时**丢掉一个零模态**（1.4e-4 直接跳到 1.3e7） | 小 shift 是必要的而不是保守的：`λ = 1/ν − α` 有相减抵消，α 越大精度损失越大；但 α 太小又会让分解接近奇异。`1e-6·trace 比值` 实测稳定 |
| **ARPACK 默认随机初值** | 同一输入两次求解结果不一致 | 固定 `v0 = default_rng(0).random(n)`。"结果不可复现"的测试等于没有测试 |

**物理语义上必须说清楚的两件事**（都在 `warnings` 里回报）：

- **载荷不影响固有频率**：`force` / `pressure` / `temperature` 会被忽略。不说明的话，
  "我加了 1000 N，频率怎么没变"会变成反复出现的疑问。
- **非零"指定位移"在特征值问题里没有意义**：特征值问题是**齐次**的，只有
  "哪些自由度被约束"这一信息参与求解。用户填了 1 mm 却毫无影响，必须提示。

### 12.2 验证：用**精确不变量**而不是"某个网格上误差小于 5%"

路线图原本给模态定的验收标准是"悬臂梁一阶频率 vs 解析解误差 <5%"。实测发现
这条标准有两个坑（详见 `docs/01` 阶段 2 的更正说明）：线性四面体在细长梁弯曲上
有剪切锁死；而且参考模量必须选对。改用下面四条**精确关系**：

| 层次 | 断言 | 实测 |
|---|---|---|
| 刚度矩阵 | 6 个解析刚体模态（3 平移 + 3 绕形心转动）满足 `K u = 0` | 相对残差 **1e-16** |
| 质量矩阵 | 平移 `uᵀMu = ρV`；转动 `uᵀMu = ρV(w²+h²)/12` | 相对差 **3e-16**（与特征值求解器无关） |
| 特征值求解 | 自由-自由**恰好 6 个**零特征值，其后才是弹性模态 | 零模态/λ₇ ≈ 4e-12；振型满足 `φᵀMφ = I`（1e-8） |
| 解析频率 | 全域滚动支承细杆的轴向频率 `f_n = (2n−1)/(4L)·√((λ+2μ)/ρ)` | 二阶收敛：误差 **6.4e-3 → 1.6e-3 → 3.9e-4 → 4.0e-5**（nx=4→32，比值恒为 4） |
| 单位链路 | `ω ∝ √(E/ρ)/L` ⇒ 同一网格按 mm/m 解释频率比**恰好 1000** | 1000.000000000008 |

### 12.3 ❌ 我在这一轮里写错的三个断言（代码是对的）

这是本轮最值得记录的部分。三条失败的断言**看起来都像是被测代码有 bug**：

| 错误断言 | 失败现象 | 真相 |
|---|---|---|
| 侧限杆频率 vs `√(E/ρ)` | 稳定偏大 **16.0%**，且加密网格**不收敛** | `u_y=u_z=0` 时材料不能横向收缩 ⇒ 有效模量是**侧限模量** `λ+2μ = E(1−ν)/((1+ν)(1−2ν))`。ν=0.3 时 `√1.3462 = 1.1602`，正好 16%。**错的是参考解** |
| 同一网格换 mm/m，频率应**完全相同** | 差 **1000 倍** | `ω ∝ √(E/ρ)/L`，单位改变的是**几何真实尺寸**（10 单位按 m 是 10 m、按 mm 是 0.01 m），频率**本来就该**差 1000 倍。**错的是物理** |
| 不同尺寸模型的放大后**绝对**变形幅度应一致 | 得到 `[8, 80, 0.8]` | 放大后的幅度应等于**各自模型尺度的 8%**；绝对量随尺寸变化才是对的。**错的是"一致性"的定义** |

判别方法：**"16% 且不随 h 收敛"是决定性线索**——离散误差一定随 h→0 消失，
不消失就说明参考解里混进了另一个模型假设。这类"测收敛阶"的做法比单点容差强得多。

### 12.4 ❌ 我的测试把后台任务留在了工作线程里 ⇒ `access violation`

`test_modal_job_matches_sync` 的第一条断言写成 `assertEqual(submitted["status"], "queued")`，
而任务可能已被工作线程取走（实测返回 `running`）。断言失败后测试**立即中止**，
后台任务仍在工作线程里跑 gmsh；下一个测试类在主线程调用 `gmsh.open`，
两边并发访问同一份 gmsh 全局状态，结果是：

```
OSError: exception: access violation reading 0x0000000000000000
```

一个**与真实失败原因毫无关系**的崩溃（报错位置在 `gmsh.open`，看起来像 gmsh 坏了）。
修正：**先轮询到任务终态再断言**，并在 `tearDown` 里排空队列
（`_drain_job_queue`）。这条已写进 `CONTRIBUTING.md` §4.2 作为硬约束。

### 12.5 🔴 结果云图**根本没有显示变形**（本轮最严重的缺陷）

### 12.6 🟠 变形放大系数被写死成**绝对坐标量**


### 12.7 验证：无法点击浏览器时，怎么把"看图"变成机器检查

顺着 §4.2（第八轮）的思路又推进了两步，都是可复用的做法：

1. **用 node 直接执行前端的 `.ts` 并断言**。Node ≥ 23 支持类型擦除，
   可以 `import './deformation.ts'`。这样前端的算法**不必在 Python 里重写一遍**

2. **对着色器做契约检查**：`verify` 读取 `resultShader.ts`，剥掉注释后断言

> 作为说明，第一版检查就匹配到了注释里的 `vec3 deformedPosition = position;` 而误报。

### 12.8 🟡 顺带修掉的历史测试噪声

### 13.1 我自己的测试抓到我自己写的 bug：`formatFrequency(null)` 返回 `0 Hz`

`formatFrequency` 的第一版是：

```ts
const value = Number(hz);
if (!Number.isFinite(value) || value < 0) return UNKNOWN_FREQUENCY_LABEL;
if (value < 1e-6) return '0 Hz';     // ← Number(null) === 0
```

`Number(null)`、`Number(undefined)`、`Number('')`、`Number(false)` **全都等于 0**，
于是"频率缺失"会被显示成 **`0 Hz`**——而 `0 Hz` 在这个界面里的含义是
"刚体模态"。把"数据缺失"说成"零频"是彻底的误导，而且正好是我在函数注释里
警告过的那种错误。

修法是在 `Number()` **之前**排掉这些值，并把入参类型从 `number`（声明）改成
`unknown`（这些值来自后端 JSON，到了这一步就必须按不可信输入处理）：

```ts
if (hz === null || hz === undefined || hz === '' || typeof hz === 'boolean') {
  return UNKNOWN_FREQUENCY_LABEL;
}
```

> 这条断言（`[null, '—']`）是我顺手加的边界用例，结果立刻失败了。
> **边界值断言的价值就在这里**：`0 Hz` 和 `—` 在正常数据下永远不会同时出现，
> 只有专门构造退化输入才会暴露。

### 13.2 `verify` 的兜底 `except` 把 traceback 吞了（已修）

排查上面那个问题时，`verify` 只报了一句
`TypeError: expected str, bytes or os.PathLike object, not list`，
完全指不出是哪一行。原因是大段物理校准被一个 `except Exception` 包住，
只把异常摘要塞进检查项细节里。

修法是在这个兜底捕获里 `traceback.print_exc()`。改完立刻看到真正的栈：

```
File "tools/tasks.py", line 608, in list2cmdline
File "<frozen os>", line 859, in fsdecode
TypeError: expected str, bytes or os.PathLike object, not list
```

### 13.3 一个真实的 Python 陷阱：循环变量泄漏把可执行文件路径覆盖成了数组

上面那个 `TypeError` 的根因是：`task_verify` 里早就存在

```python
for index, node in enumerate(cube["nodes"]):   # cube["nodes"] 是 [[x,y,z], ...]
```

而 Python 的 `for` 变量**会泄漏到外层作用域**。我在同一个函数里新加的代码用了
`node` 表示 node 可执行文件路径，于是它被循环覆盖成了**一个节点坐标数组**
`[x, y, z]`，最终作为 argv 的第一个元素传给 `subprocess.run`。

修法：把可执行文件路径改名为 `node_bin`（不与业务数据重名）。

> 教训：在长函数里，**别给"环境/工具类"变量起与业务数据同名的名字**。
> `node` 既可能是"Node.js 可执行文件"也可能是"网格节点"，同名就会互相覆盖。

这一步挡的是"字段名漂移"：后端把 `mode_shapes` 改名之后，界面只会**静默地

## 十四、第十一轮：项目持久化（"项目"成为一等实体）

在此之前后端**根本没有"项目"这个实体**：仪表盘上的列表是 `App.tsx` 里一个硬编码
数组（`{ id: '1', title: 'Aerodynamic Wing v3' }`），新建项目只存在浏览器内存里。
刷新就丢、重启更是全丢，**也无法被引用或共享**。

"可协作"的前提是存在一个**可以被共享的对象**。你说"我那个悬臂梁项目"，对方要能
拿到它——而它原先在你的浏览器内存里。

| 项 | 内容 |
|---|---|
| `sqlite_store.py` | 抽出 SQLite 存储基类：连接、事务、**显式关闭**、幂等加列迁移；`MaterialStore` 改为继承（18 个已有用例守住重构） |
| `project_store.py` | 表 `projects`：id / 标题 / 描述 / 分析类型 / 是否私有 / 创建与更新时间 |
| `projects.py` | `/api/projects` 增删改查 + `/api/project-metadata` |
| 前端 | 仪表盘改为挂载时拉取、新建走 POST、卡片可删除；补上加载中 / 失败可重试 / 空列表三种状态 |

### 14.1 为什么把 `_cursor` 抽成基类

`material_store` 里的 `_cursor` 上下文管理器编码了一个**真实踩过的 bug**：

```python
with sqlite3.connect(...) as conn:   # ← 只提交事务，**不关闭连接**
```

这样每次调用都泄漏一个句柄，在 Windows 上会一直锁住数据库文件。项目曾因此在测试里
出现 14 个 tearDown 失败。现在有了第二个需要持久化的实体（项目），这类规则写两遍
一定会漂移——所以抽到 `sqlite_store.SqliteStore`，谁的存储都继承它。
（同一个理由在 `fe_utils.py` 的模块文档里已经写过一次。）

### 14.2 三个刻意的设计决定

| 决定 | 理由 |
|---|---|
| **ID 由服务端生成**（`uuid4().hex[:12]`），请求体里带 `id` 直接 422 | 原前端用 `Date.now().toString()`：既可预测、又取决于客户端时钟。而且客户端能自选主键就意味着**能覆盖别人的记录**。也不能"静默忽略"——那会让用户以为按自己的 ID 存下了 |
| **排序用 `rowid` 而不是 `created_at`** | 时间戳只精确到秒，同一秒内建的两个项目会并列，"最新的在最前"就变成不确定的顺序。测试里会时好时坏（典型的 flaky） |
| **`owner_id` 与鉴权故意不加** | 一个"存在但没人校验"的属主字段比**没有**更危险：它会让人以为数据已经隔离了，从而写出依赖这个假设的代码。真正接登录时再加列——`SqliteStore.migrations` 就是为这种演进准备的（材料库已演示过一次） |

### 14.3 🔴 接上真实接口就会崩的一行代码

旧代码渲染创建时间用的是：

```tsx
<span>{proj.createdAt.toLocaleDateString()}</span>
```

`types.ts` 里 `Project.createdAt` 声明为 `Date`，所以类型检查完全通过。但**后端返回的
是 ISO 字符串**——字符串没有 `toLocaleDateString` 方法，接上 HTTP 的那一刻就会抛
`TypeError: proj.createdAt.toLocaleDateString is not a function`。

这类"类型声明与运行时数据不一致"的缺陷，`tsc` 永远发现不了：声明是开发者自己写的，
不是从接口生成的。修法是把时间戳解析**集中到一个边界**上
（`utils/projectsApi.ts` 的 `toProject`），界面其余部分才可以放心地认为拿到的是 `Date`。

`verify` 里为此写了一条**显式的回归断言**：

```js
// 字符串不是 Date —— 旧代码就是这么崩的
check('字符串不是 Date（旧写法必然抛错）',
      typeof '2026-03-18T00:00:00+00:00'.toLocaleDateString === 'undefined');
```

### 14.4 界面不说谎：三种状态都要有

前端原先假定"列表一定拿得到"。改成真实接口后必须区分三件事，否则用户会误判：

| 状态 | 显示 |
|---|---|
| 加载中 | `加载中…`（而不是空列表） |
| 失败 | 黄色横幅 + **具体原因**（`describeProjectError` 会区分"无法连接后端"/404/422/5xx）+ 重试按钮 |
| 空 | 明确写"还没有项目"，并说明项目会存在后端数据库里 |

后端不可用时显示空列表，用户的第一反应是"我的项目被删光了"——这不是体验问题，
是在传达错误事实。创建失败时弹窗也**留在原地**并给出原因，而不是关掉让用户以为建好了。

### 14.5 验证：跨完整后端重启

这一轮的核心承诺是"项目不会丢"，所以验证必须真的重启一次进程：

```
POST /api/projects             → id=66f377400f56，标题"重启存活检查 中文标题"
tools/tasks.py stop            → 后端进程结束
tools/tasks.py dev --detach    → 后端进程重新起来

```

### 14.6 一个客户端陷阱：PowerShell 5.1 会把中文显示成乱码

用 `Invoke-RestMethod` 做手工验证时，中文标题显示成 `éå¯åæ´»æ£æ¥`，看起来像后端
存错了。**实际不是**——直接读 SQLite 看到的是正确的中文。原因是 Windows PowerShell 5.1：

- **发送** body 时按 ANSI 编码字符串 ⇒ 中文变成 `?`；
- **解析** JSON 响应时按 ISO-8859-1 解码 ⇒ 中文变成 `éå¯...`。

两条都只发生在**客户端**。所以断言"中文能不能原样往返"必须用能显式控制编码的
客户端（本项目的 `tools/tasks.py` 用 `urllib` 并显式 `encode/decode('utf-8')`；
手工验证时改用 Python 脚本）。这条已写进 `CONTRIBUTING.md` 的常见问题。

## 十五、第十二轮：登录与用户隔离

上一轮项目已经持久化，但后端**不知道"你是谁"**：`isLoggedIn` 只是前端一个布尔量，
点一下"开始仿真"就算登录了。结果是同一个后端上所有人共用一份项目列表，
任何人都能改名/删除别人的项目。这一轮补上用户与归属。

### 15.1 口令与会话：两个"写错就救不回来"的地方

| 决定 | 理由 |
|---|---|
| `hashlib.scrypt`（标准库，内存硬） | 对 GPU/ASIC 暴力破解的抵抗远好于 PBKDF2。参数显式给足：`n=2^14, r=8, p=1`（约 16 MB/次），符合 RFC 7914 对交互式登录的推荐量级 |
| **参数写进哈希串**（`scrypt$n$r$p$salt$hash`） | 最容易被忽略的一条。若把 `n/r/p` 留在代码常量里，**改一次参数就等于让所有老用户登不上**。写进串里之后：老口令用自己的参数验证、新口令用新参数、登录成功时顺手 `needs_rehash` 升级 |
| 每用户独立随机盐 | 共用盐会让彩虹表/批量破解重新变得可行 |
| `secrets.compare_digest` 而不是 `==` | 后者在第一个不同字节处提前返回，泄露"前几个字节猜对了"的时序信息 |
| 参数上限校验 | 哈希串来自**数据库**。若原样交给 scrypt，一个畸形串（比如 `n=1073741824`）就能让进程分配巨量内存。校验失败一律返回"口令不正确"，不抛异常 |
| **令牌只存哈希** | 数据库被读走时拿不到可直接使用的令牌。这里用普通 SHA-256 而不是 scrypt：令牌是 32 字节高熵随机串，不存在"被猜到"的问题，而每个请求都要查一次会话，用慢哈希会让每个 API 调用多花几十毫秒 |
| **不用 JWT** | ① 服务端会话可以**吊销**（登出、改密、踢设备都是删一行；JWT 想做到还得再维护黑名单）；② 不必自己实现密码学——手工拼 HMAC/base64url 并校验声明是经典高危动作（漏校验 `alg`、漏校验 `exp`、时序比较……）；③ 过期判断写在 SQL 的 `WHERE expires_at > ?` 里，不会因为某处忘记判断而放行过期会话 |
| 不给用户名枚举 | "用户不存在"与"口令错误"返回**同一句话**，并且用户不存在时也陪跑一次假哈希，让两条路径耗时接近 |

### 15.2 项目隔离：`owner_id` 是必填参数，没有"返回全部"这个模式

存储层的方法签名是 `list_projects(owner_id, include_unowned=False)`——
`owner_id` **必填**。道理很简单：如果把 `owner_id=None` 解释成"不过滤"，
任何一处忘记传参的调用都会静默地把所有用户的数据混在一起，
而这正是"用户隔离"要防的事。宁可让调用方多写一个参数。

同理，别人的项目返回 **404 而不是 403**：403 等于确认"这个 id 存在，只是不是你的"，
可被用来探测别人有哪些项目。（代价是用户不容易区分"我的项目没了"与"这不是我的项目"，
所以界面上把"未归属"这类状态显式标出来。）

`ownerId` 也不在可更新字段里，**两层都挡**：请求模型 `extra="forbid"` → 422；
存储层 `_UPDATABLE` 白名单 → 400。只挡一层不够：第一层防接口，
第二层防"以后有人加了个内部调用"。

### 15.3 🔴 我自己引入、并靠检查真实数据发现的缺陷：自动接管把用户的项目划走了

初版为了"让遗留数据不至于消失"，写的是：

```python
if store.count_users() == 1:
    get_project_store().adopt_unowned(user["id"])   # 第一个注册的用户接管所有无主项目
```

看起来合理，实际闯了祸：

1. `tools/tasks.py verify` 会注册**固定的测试账号** `verify_alice`（这样不会每次运行
   都往库里塞新用户）；
2. 它成了第一个用户 → `adopt_unowned` 触发；
3. 开发者此前在浏览器里手工建的项目 `owner_id` 是 NULL（那时还没有用户概念）
   → **被静默划给了测试账号**。

用户下次登录会发现项目不见了，而且**不会有任何报错**——
这是最糟的一类数据事故：静默、不可见、看起来像"数据丢了"。

**怎么发现的**：verify 输出里有一句 `新项目出现在自己的列表最前 → 2 个项目`，
而我预期只有 1 个。于是直接打印真实数据库内容，看到 `test1` 的 owner 是
`verify_alice`。

**修正**为"可见 + 显式认领"：

| 状态 | 行为 |
|---|---|
| 无主项目（`owner_id IS NULL`） | 对**所有**已登录用户可见（列表里 `ownerId` 为 `null`，界面标"未归属"） |
| 修改/删除 | **只允许属主本人**；无主项目必须先认领 |
| 认领 | `POST /api/projects/{id}/claim`，幂等；SQL 里带 `WHERE owner_id IS NULL`，因此**不可能**变成"任意项目过户" |

已受影响的数据还原为无主。**教训：静默改变数据归属，比"看得见但要手点一下"危险得多。**
凡是"为了用户体验而自动改变归属/权限"的逻辑，都要先问一句：
**"如果这段逻辑被一个非人类账号触发，会发生什么？"**

### 15.4 前端：`localStorage` 会抛异常，"连不上后端"与 401 必须分开

`utils/authApi.ts` 把三件容易写错的事抽了出来：

1. **`localStorage` 会抛**：Safari 隐私模式、被策略禁用的存储、配额满。
   直接写在组件里，用户看到的是白屏。现在读写清三条路径都 `try/catch`，
   并且支持注入假存储（`verify` 用一个"总是抛异常"的假存储验证这条路径）。
2. 没有令牌时**不发** `Authorization: Bearer undefined`——那会让后端的错误信息
   变得莫名其妙。直接不带这个头，让后端回一个干净的 401。
3. **401 与"连不上后端"要分开**：前者要清令牌并回登录页，后者要先把服务起起来。
   混为一谈会让用户反复重试一件永远不会成功的事。

会话恢复也刻意做成"向 `/auth/me` 问一次"，而不是"本地有令牌就当已登录"——
**只信本地令牌是不够的**：它可能已过期，或者在后端被登出了。

**关于令牌存 `localStorage` 的代价**：它无法被 `HttpOnly` 保护，出现 XSS 时令牌可被
读走；改用 `HttpOnly` Cookie 就得同时处理 CSRF。对当前这种本机/小范围部署，
Bearer + `localStorage` 复杂度更低且不引入 CSRF 面——**这一点写进文档，不假装它更安全。**

### 15.5 验证：单测覆盖不到 Header 依赖注入，所以必须在真实 HTTP 上验

新增 65 个后端用例（合计 **249**）与 12 项 `verify` 检查（合计 **52**）。

有一条特别值得说：单测里是**直接构造 `Authorization` 头**调 `require_user` 的，
因此**没有走 FastAPI 的 Header 依赖注入**。那条链路（`Header(default=None)` 的解析、
401 时带 `WWW-Authenticate`）只有真实 HTTP 能验。所以 `verify` 用两个固定测试账号
（`verify_alice` / `verify_bob`）跑了完整流程：

```
未登录 / 非 Bearer / 伪造令牌       → 401
登录响应                            → 含令牌，且**不含口令哈希**
/auth/me                            → 对应正确用户
口令错误 vs 用户不存在               → 完全相同的 401
alice 建项目 → bob 看/读/改/删       → 看不到；读改删都是 404；且无副作用
遗留项目（直接写库造出 owner_id=NULL） → 可见但未归属 → 认领前不可删
                                     → 认领后归属变为自己 → 可改名
                                     → bob 不能认领已属于 alice 的项目
```

最后这组"遗留项目"检查需要**直接往数据库插一行**才能造出前置状态
（HTTP 接口创建的项目一定有属主）。这是刻意为之：它验证的是本轮最关键的策略修正，
而那个状态没法只靠接口构造。`verify` 跑完会把这行删掉。

### 15.6 仍然开放的地方（如实记录）

`/api/solve`、`/api/upload-geometry`、`/api/generate-mesh` 等**仍不要求登录**。

- 影响面：共享部署下任何人都能占用算力、上传文件；但**项目数据本身是隔离的**。
- 为什么不一起改：那会改变几乎所有现有端点与 `verify` 的物理校准流程
  （需要先登录再跑解析解对照），是一次独立的、需要单独验证的改动。
- 已在 README 的"已知限制"里标明，并在 `docs/01` 列为下一项。

## 十六、第十三轮：计算类端点的访问控制

上一轮只保护了项目端点。`/api/solve`、`/api/upload-geometry`、`/api/generate-mesh`
等**仍对所有人开放**——共享部署下任何人都能占算力、传文件、花掉 DeepSeek 的额度。
项目数据是隔离的，但**计算资源不是**。

### 16.1 用路由级依赖，而不是给每个端点加参数

```python
router = APIRouter(dependencies=[Depends(require_user)])
```

覆盖 solver / thermal / modal / geometry / jobs / materials / constraints /
ai_assistant 八个 router。两个具体理由：

1. 这些端点**不需要知道"你是谁"**——不像项目端点要按属主过滤，加一个用不到的
   参数只是噪音，还会让每个端点签名都多一截。
2. 更实际的是：**40 多个既有测试是直接调用端点函数的**（不经 HTTP），
   逐个加必填参数会让它们全部失效——而那一层测试正是物理正确性的防线
   （FL/AE、解析应力场、热传导 q=kΔT/L、模态二阶收敛都在那里）。
   路由级依赖只在 HTTP 层生效，直接调用完全不受影响。

实测：改完 249 个用例全绿，`verify` 里那 4 项"未登录被拒"也全通过。
**如果当初选了逐端点加参数，这一轮就得同时改几十个测试**——那正是不该做的事。

### 16.2 前端的令牌获取：从存储读，不穿透组件树

新增 `currentAuthHeaders()`，任何一处 axios 调用都能直接用：

```ts
export function currentAuthHeaders(extra = {}) {
  return authorizationHeader(readStoredToken(), extra);
}
```

令牌本来就是这个 App 的**会话级状态**，而存储已经是它的持久层。
再把它作为一个 prop 从 `App` 传到 `Workbench` 再传到 `MaterialSelector` /
`AIAssistantPanel`，只会制造两个真相（以及"某个分支忘了传"的 bug）。

值得单独说的是**加载顺序**问题：这些组件的 `useEffect` 是在 token 写进存储**之后**
才发请求的，所以读存储总是拿到当前值；而如果是"模块加载时读一次并缓存在变量里"
就会在登录前读到 `null`——这是这类写法的经典坑，用函数取值天然避开。

### 16.3 401 不是"算不出来"：别把用户引向错误方向

网格划分与求解失败时，原来的代码会**自动触发 AI 诊断**。加了访问控制之后，
"登录失效"也会走到同一条失败路径——于是用户会看到 AI 在分析"网格为什么失败"，
而真正的原因是他需要重新登录。**这属于把用户引向完全无关的方向。**

现在的分流：

| 情况 | 行为 |
|---|---|
| 401 | `notifySessionExpired()` 广播事件 → App 清令牌 + 回登录面板；**不触发** AI 诊断 |
| 其它失败 | 保持原样（提示原因 + 可选 AI 诊断） |

为什么用事件而不是回调：`Workbench` 之下还有 `MaterialSelector` / `AIAssistantPanel` /
`ImportModal`，把回调层层透传既啰嗦又容易漏。项目里已有的 `apply-ai-params` 就是
这个套路，保持了一致。

### 16.4 multipart 上传：不要手写 Content-Type

上传 FormData 时显式设置 `Content-Type: multipart/form-data` 是常见但危险的写法：
**boundary 必须由浏览器自己生成**，手写（或某些封装把 boundary 丢掉）会让后端
解析不出分片。改为只带认证头，让 axios/浏览器决定 Content-Type。

实测（Python 手工构造 multipart，带令牌）：

```
POST /api/upload-geometry   无令牌=401   带令牌=200  -> render_filename=verify_394153.stl
```

### 16.5 🟡 我自己踩的两个工具坑（都不是产品代码的问题，但值得记）

**坑一：`Path.write_text()` 在 Windows 上会把 `\n` 写成 `\r\n`。**

这一轮我用 Python 脚本批量改后端文件（加 router 依赖），结果 13 个文件变成了 CRLF。
`.gitattributes` 声明了 `eol=lf`，所以 git 提交时会规范化并给出警告；工作区与仓库
不一致也不会造成错误的提交内容，但会产生"看起来改了其实没改"的噪音 diff：

```
git status -> M（13 个文件）
git diff   -> 空
```

根因是**索引的 stat 缓存过期**，`git add` 刷新即可。已在文档里记下，
以后用脚本改文件要么显式 `newline="\n"`，要么改完统一规范化一遍。

**坑二：我用 `git add -A -- backend frontend tools` 误把用户的两个上传件加进了暂存区。**

`-A` 会连**未跟踪**文件一起加。这个仓库里 `backend/uploads/零件1.STEP` 与
`.STEP.stl` 是刻意不纳入版本控制的用户文件，之前每一轮我都逐个列文件名提交，
就是怕这个。发现后立即 `git restore --staged` 撤出（文件本身没动）。
**教训：这个仓库里永远不要用 `git add -A` / `git add .`，一律列明文件名。**

## 十七、第十四轮：项目配置持久化

在此之前"项目"只是一个名字 + 描述：几何、材料、边界条件、网格与求解设置
**全在浏览器内存里**。关掉页面就没了——重新打开项目是一个**空白工作台**。
也就是说，"项目"这个概念的核心承诺（下次接着做）实际上是空的。

### 17.1 校验策略是分级的，这是刻意的

配置文档里有两类东西，性质完全不同：

| 字段 | 策略 | 理由 |
|---|---|---|
| `geometryFilename` | **从严**（复用上传时的同一套规则：纯文件名 + 扩展名白名单） | 前端之后会拿它去请求几何端点；存储时校验一次，路径穿越之类的东西就进不了库 |
| `boundaryConditions` | **从严**（直接 `BoundaryCondition`，`extra="forbid"`） | 它们会被原样送回求解器；字段拼错必须当场 422 |
| `meshSettings` / `solverSettings` | **从宽但有界**（只要求是 JSON 对象，总量 256 KB） | 它们是**界面状态**，形状随界面迭代变化。在这里逐字段钉死会把后端和前端 UI 耦合起来——每改一次界面都要同时改后端，而这类改动本不该有后端成本 |

另外 `geometryFilename` **不要求文件存在**：几何可能已被清理，但用户配好的边界
条件不该因为文件没了就丢掉。

### 17.2 两个容易忽略的语义区分

**404 与 200+null 必须分开。**

| 情况 | 返回 |
|---|---|
| 项目不存在，或不属于当前用户 | **404** |
| 项目存在但从未保存过配置 | **200 + `setup: null`** |

混在一起，前端就会把"还没配过"当成"项目没了"。

**坏 JSON 按"空"处理并留日志，而不是 500。** 500 的话用户完全不知道发生了
什么，也不知道配置其实已经丢了。而且这条兜底必须**只有一份实现**：

初稿在列表里用 `bool(setup)` 判断 `hasSetup`（字符串非空就算"已配置"），
而 `get_setup` 会解析失败后返回空。于是出现"列表说已配置、打开却是空的"——
一个很小但确实在骗人的不一致。是 `test_corrupt_json_is_treated_as_empty_not_a_crash`
把它抓出来的。现在两处共用 `parse_setup()`。

### 17.3 一个数据保真问题：`model_dump()` 会把文档"充气"

第一次实测"保存后读回"时，得到的结论是"不一致"。差异打印出来是：

```
读回来多了 .boundaryConditions[0].description = None
读回来多了 .boundaryConditions[0].displacement = None
... （每个边界条件多出 11 个 null 字段，17 个里 11 个是空的）
```

`model_dump()` 会把所有**未填**的可选字段补成 `None` 一起存进去。数据没丢，
但文档被"充气"了——对一份有 100 个边界条件的配置来说，这会白白吃掉几倍的
存储与传输，也让"存进去什么、读回来就是什么"不再成立。

改用 `exclude_none=True` 后，库里是 **620 字节**的紧凑文档（实测
`"description":null` 已不在其中）。

但**响应里那些 null 又回来了**——因为响应会经过 `SimulationSetupResponse`
（Pydantic 模型）再序列化一次，而模型序列化默认包含所有字段。这不是数据被改，
是**响应模型在起作用**（好处是响应也受模型校验）。所以正确的断言是
"值完全一致（把显式 null 与字段缺失视为等价）"，而不是字节相同。

> 教训：**别猜，直接打印差异。** 我一开始两次猜测原因（先是以为
> `exclude_none` 没生效，再是以为后端跑的是旧代码），都不对；写一个逐字段
> diff 的脚本，一次就定位到了。

### 17.4 前端的三个关键决定

**自动保存靠"签名"判断有没有真的变。** `JSON.stringify` 保留键的插入顺序，
于是 `{a:1,b:2}` 与 `{b:2,a:1}` 会得到不同的字符串——用它做变化判断会**假阳性**，
每次重渲染都写一次库。所以用递归按键排序的 `stableStringify`，并且签名里
**不含 `version`**（版本只在形状变化时改，不该触发保存）。

**恢复时对不认识的内容丢弃并报告。** 存下来的文档可能是旧版前端写的。
`restoreSetup` 对类型不对的字段一律丢弃并产生一条警告（"几何文件名格式不对，
已忽略"），而不是让界面进入半损坏状态——把字符串当成边界条件数组用，
比明确报错糟得多。

**保存状态必须如实。** `error` 绝不能显示成"已保存"：用户会以为配置存下来了，
下次打开才发现全丢。状态条会显示具体原因并提供重试；`describeSaveStatus`
的断言里专门有一条"失败文案不含'已保存'"。

另外，生成网格/求解**前**会先落库：耗时任务可能跑几分钟，用户在中途刷新或
换设备时不该丢掉刚配好的东西。

### 17.5 我这一轮写错的测试数据（代码是对的）

`verify` 里新增的 node 断言第一次跑就失败了，两条都是**我的测试数据**写错：

1. **"签名与键顺序无关"失败**：我为了测键顺序，手写了一个 `reordered` 对象，
   但其中的 `solverSettings` **漏了 `solverType`**。签名正确地检测出了这个
   真实的内容差异——所以失败的是我的测试数据，不是签名算法。
2. **"每一项丢弃都有说明"期望 3 条警告、实际 4 条**：我忘了版本不符本身也会
   产生一条警告（1 条版本 + 3 条字段）。期望值写错了。

两条都在注释里写清了正确期望，避免下一个人以为是代码的问题。

## 十八、第十五轮：项目共享（"可协作"的核心）

前面几轮把地基铺完了：项目能持久化、配置能持久化、有用户、有隔离。但**所有人
还是只能看到自己的项目**——前端侧边栏那个 `Shared with me` 一直是个占位链接。
"协作"缺的正是"把项目交给别人"。

### 18.1 权限判定必须只有一个入口

```python
ProjectStore.access_role(project_id, user_id) -> owner / editor / viewer / unowned / None
```

所有端点都问这一个问题。理由很直接：**权限逻辑一旦散落在各个端点里，就一定
会出现"某处忘了判断"的漏洞**，而这类漏洞不会报错、也不会被正向测试发现。
集中之后，改规则也只改一个地方。

角色只有两个**可分配**值（`viewer` / `editor`），刻意没有 `admin`：
角色越少，"谁能做什么"越不容易说错。

| 角色 | 读 | 改配置 | 改名/删除/管理共享 |
|---|---|---|---|
| owner | ✅ | ✅ | ✅ |
| editor | ✅ | ✅ | ❌ |
| viewer | ✅ | ❌ | ❌ |
| unowned | ✅ | ❌ | ❌ |

这里有一个容易搞混的点：`unowned` **不是一种角色**，而是"这个项目没有属主"
这一事实。它带不来任何写权限——否则任何人都能改动别人还没认领的遗留数据，
而"可见但不可改 + 显式认领"正是上一轮刻意建立的规则。

### 18.2 复合主键，而不是每次插入一条新记录

```sql
PRIMARY KEY (project_id, user_id)
```

加上 `ON CONFLICT ... DO UPDATE SET role`，于是"再次共享"就是**改角色**，
而不是堆出第二条记录。如果允许堆重复：取消共享时说不清该删哪条，
"他到底是什么角色"取决于行的顺序——一个不会立刻暴露、但很难排查的问题。

### 18.3 三处错误码刻意不同

| 情况 | 返回 | 理由 |
|---|---|---|
| 分享给不存在的用户名 | **404** | 是"没有这个人"，不是"参数错"（400 会让人以为自己的请求格式有问题） |
| viewer 改配置 | **403** | 他**已经知道项目存在**（列表里看得见、配置也读得到）。此时返回 404 只会让人困惑；404 的用途是对"不知道存不存在"的人隐藏信息 |
| 非属主改名/删除 | **404** | 存储层的 SQL 本来就按属主限定，自然就是 404 |

同一份代码里出现 403 与 404 两种"没权限"，看起来不一致，但**判断依据是
"对方是否已经知道这个东西存在"**。把这条写进文档，免得下一个人"统一"成一种。

### 18.4 前端：进来就说清楚，而不是等保存时才拒绝

两个诚实之处：

1. **工作台顶部一进来就显示权限提示条**（"这是别人共享给你的项目：你可以修改
   仿真配置，但不能改名、删除或再分享给别人"）。等到用户配了半小时、
   点保存时才被拒绝，是很糟的体验——何况他可能会以为是自己操作错了。
2. **viewer 的保存状态显示"只读 · 不会保存"，而且根本不发请求**。
   悄悄不发请求是最坏的做法：用户会以为配置存下来了，下次打开才发现是空的。
   `describeSaveStatus` 因此多了一个 `readonly` 取值。

界面判权限的口径与后端 `can_edit/can_manage` **严格一致**。不一致的后果是
"界面允许操作、后端 403"——用户会以为系统坏了。所以 `projectsApi.ts` 里的
`canEditProject` / `canManageProject` 是后端那两个静态方法的镜像，并且
`verify` 用 node 逐条断言了这个真值表。

### 18.5 我又一次在 JSX 里写错了注释

把 `{/* 共享：只有属主能管理 */}` 写成了 `{/* 共享：只有属主能管理 -->`。
`tsc` 报的是**一连串**"JSX element 'div' has no corresponding closing tag"，
从第 382 行一路报到 668 行，完全指不到真正出错的那一行（615）。

排查过程值得记：我先怀疑标签不配平，写了个脚本统计 `<div>`/`<span>` 的开闭
数量——**全部配平**；然后用 `git diff` 看自己改了什么，才在 diff 里看到那个
缺掉的 `*/}`。

> 教训：**`tsc` 的 JSX 语法错误会向外层冒泡，报的位置不是出错的位置。**
> 遇到"一大串闭合标签找不到"时，直接看你**最近改过的那几行**，
> 而不是从第一个报错位置往下读。另外这个页面的那个 `{/* ... -->` 里，
> `-->` 还是从注释里粘出来的写法，两处混用最容易出这种错。

### 18.6 验证：每个写端点都要同时测"能"与"不能"

新增 38 个用例（合计 **314**）与 13 项 HTTP 检查（合计 **78**）。

权限这类逻辑最容易出的问题是"某处忘了判断"，**只测正向是发现不了的**。
所以对每一个写操作都成对断言：

```
改配置：  viewer -> 403      editor -> 200
改元信息：editor -> 404      owner  -> 200
删项目：  editor -> 404      owner  -> 200
清空配置：editor -> 403      owner  -> 200
看名单：  viewer -> 403      owner  -> 200
```

另外专门断言了"共享响应不含任何口令字段"——共享名单要显示用户名和显示名，
很容易顺手把整个用户对象塞进响应里。

**遗留**：这是"各自保存"，不是实时协同编辑——两个人同时改配置会互相覆盖
（后保存的赢）。已登记在 `docs/01`。

## 十九、第十六轮：关掉公开的几何文件目录

我连续两轮把这条登记在"已知限制"里。它现在更值得修：项目已经能共享、每个账号只
看得到自己的项目，但**知道文件名的人仍能直接下载别人上传的 CAD 原件**——
两条承诺互相矛盾。

### 19.1 当时为什么没修，以及现在怎么修

`uploads/` 是 `StaticFiles` 直接挂载的。给静态目录加鉴权看起来是一行的事，
但**没用**：three.js 的 `STLLoader`/`GLTFLoader` 不会带 `Authorization` 头，
前端拿不到文件。这就是当初把它列进"已知限制"而不是顺手修掉的原因。

现在的做法换了思路——**不让加载器去发那个请求**：

```
fetch（带认证头） -> Blob -> URL.createObjectURL -> blob: URL 交给加载器
```

- 后端新增 `GET /api/geometry/{filename}/download`（走 geometry router 的
  路由级依赖，因此需要登录）。文件名仍走 `resolve_upload_path`（防穿越 +
  扩展名白名单），Content-Type 用一张显式的表——`.step`/`.iges` 用
  `mimetypes.guess_type` 在很多系统上猜不出来。
- **移除公开的 `/uploads` 挂载**。这一步是关键：下载端点再多，只要静态目录还在，
  洞就还在。
- 前端改成上面的流程；加载器拿到的 `blob:` URL 是普通的、不需要认证的 URL。

### 19.2 顺带补上一个真实缺陷：重新打开项目时视口是空的

上一轮做配置持久化时，恢复里写了 `setModelName(restored.geometryFilename)`
——恢复了**名字**，却没有取回**模型本身**。于是重新打开一个保存过的项目：
配置都在、网格设置都在、就是视口里什么都没有。

这个缺陷在上一轮没被发现，是因为当时的注意力都在"配置有没有存下来"上；
这一轮改预览加载路径时才顺着看到。**现在恢复配置时会一并加载几何预览。**

顺带说明：`meshData`（节点/单元）没有持久化，所以重新打开时能显示的只有几何
预览，不能直接显示上次的云图。这一点在预览失败时的提示里也写清楚了：
"仿真配置、网格划分与求解不受影响"。

### 19.3 前端：把"取文件"做成可注入依赖的纯逻辑

新增 `frontend/utils/modelSource.ts`。`fetchImpl` 与 `createObjectURL` 都能替换，
于是 `verify` 能用 node 完整断言成功与各种失败路径，**不需要浏览器**：

| 断言 | 为什么值得钉住 |
|---|---|
| 下载地址拼接、文件名 URL 编码 | 拼错就是 404 |
| **预览名规则与后端一致**（`<原名>.stl`） | 不一致只会表现为"视口是空的"，极难排查 |
| 非法文件名在**发请求之前**被挡 | 客户端也多一层防护，且不把 `../` 拼进 URL |
| 401/404/400/网络失败四种文案分开 | 混在一起会让用户反复重试一件不会成功的事 |
| 成功时返回可 `revoke` 的 blob URL | 大 STL 有好几 MB，不 revoke 就是内存泄漏 |

**认证头由调用方传入，而且 `headers` 是必填的。** 两个原因：

1. 这个模块不该知道令牌放在哪（将来换成 HttpOnly Cookie 只用改调用方）；
2. 让它能被 node 单独执行——跨模块的相对导入在 **Node 的 ESM 解析器**下需要
   显式扩展名，而 TS/Vite 允许省略。第一次跑就撞上了这个差异：
   `Cannot find module '.../utils/authApi'`。当时 `modelSource.ts` 里有一句
   `import { currentAuthHeaders } from './authApi'`，把它去掉就同时解决了两个问题。

`headers` 设为必填还有个好处：**"忘记带令牌"在编译期就暴露**，而不是运行时变成
一个和"真正登录失效"混在一起的 401。

### 19.4 verify 的这组检查：先真的上传，再下载

预览 STL 只在**上传**时生成，开发机的 `uploads/` 里不一定有现成文件；而且
"上传 → 下载"这条往返本身就值得验证。所以：

```
上传一个临时 STL（带令牌）
  -> 无令牌下载该文件 -> 401
  -> 带令牌下载 -> 200，Content-Type=model/stl，129 字节
  -> GET /uploads/<同一文件> -> 404（公开目录确实关了）
删除临时文件
```

实测输出（129 字节是我构造的最小 STL：一个三角形）。

### 19.5 小结：README 里那句"已知限制"要跟着改

修完之后有两处文档必须同步，否则文档自己在说谎：

- README 的"已知限制"里"⚠️ `/uploads/` 仍开放"要改成"✅ 需登录"；
- `docs/01` 的第 21 项要标为已完成。

这类"修完忘了改状态"的漂移，我已经在文档里吃过几次亏（用例数、verify 项数都
漂移过）。所以本轮顺手把它们一起改正了。

## 二十、第十七轮：网格质量（"我的网格行不行"）

### 20.1 为什么先做"形状质量"

用户最常问的一件事是"我的网格行不行"，而在此之前这个项目只能回答"生成了 N 个
单元"——那不是答案。网格能不能用其实是**两个独立问题**：

1. **单元形状**（本轮）：畸形单元（尤其压扁的"刀片"）让刚度矩阵病态，应力在
   这些单元里出现毫无意义的尖峰；
2. **单元密度**（下一轮）：形状再好，网格太粗结果也不准。

本轮只做第 1 件，并且在结论里**反复强调第 2 件还没做**（见 20.5）。

度量选的是：对每个四面体取 6 条棱长的均方根 `L` 与体积 `V`，

```
q = V / (L³ / (6√2))   ∈ (0, 1]
```

分母是"棱长为 L 的正四面体体积"，所以 **q = 1 当且仅当单元是正四面体**。

选它的唯一理由是**可解析验证**：正四面体恰好 1、直角四面体可手算
（`(1/6)·6√2 ÷ (3/2)^{3/2} ≈ 0.7698`）、共面恰好 0、朝向反了为负、整体缩放不变。
换成"最小/最大棱长比"之类看着合理的指标，就没法把实现钉住了——而这个项目
已经吃过"只断言'结果看起来合理'所以漏掉数量级错误"的亏。

### 20.2 一个真 bug：`einsum` 到底沿哪条轴求和

第一版 `edge_lengths` 写成了：

```python
delta = points[:, cells[a]] - points[:, cells[b]]      # 形状是 (3, n_elements)
np.sqrt(np.einsum("ij,ij->i", delta, delta))           # 却按"末轴"求和
```

`np.einsum("ij,ij->i")` 沿**末轴**求和，而 `points[:, cells[a]]` 的末轴是"元素"，
不是"坐标分量"。后果是它算出 `(3,)`——每条棱一个**坐标分量**，而不是每个单元
一个棱长。单元数为 1 时看着还像对的，单元一多就完全错了：

- `edge_lengths` 本该返回 `(1, 6)`，实测 `(3, 6)`；
- 正四面体的质量本该**恰好 1**，实测 **5.196152 = 3√3**；
- 到端点层还会炸出 `operands could not be broadcast (1571,) (3,)`。

抓到它的不是"检查结果是否有限/非 NaN"（那种断言在这种情况下会**全部通过**），
而是"正四面体必须恰好为 1"这条解析断言。这是本项目第三次由解析值而不是
"看起来正常"抓到真 bug。

修正就是补一个转置（`.T`），并把原因写在注释里——因为"漏转置"在 NumPy 里
太容易重犯，而单元数为 1 的测试又恰好掩盖它。

### 20.3 负体积不取绝对值

有符号体积是有意保留的：**朝向反了（雅可比为负）比"形状差"更严重**，必须能
被数出来。所以 `q < 0` 时不去绝对值，而是单独统计 `non_positive_volume_count`
与 `non_finite_count`，并在结论里优先报出来。取绝对值会把"单元朝向错误"
伪装成"质量不错"，那是最坏的一种"看起来正常"。

### 20.4 直方图的所有箱加起来必须等于单元总数

`np.histogram` 对越界值默认是**丢弃**，而落在 `[0,1]` 之外的值（负质量、
数值异常）恰恰是最需要被看到的单元。所以先 `clip` 到 `[0,1]` 再统计，
保证"各箱计数之和 = 单元总数"，并用测试钉住（含 `-5` / `7` 这类越界值）。
前端也据此检查一次（`histogramIsComplete`），不自洽就明说，而不是照画不误。

### 20.5 结论句必须一直带着"形状好 ≠ 够细"

后端 `_verdict()` 无论网格多好都会附上"密度是否足够要看收敛性"，verify 断言
这句话里必须出现"收敛"，前端**原样显示**不改写。原因很简单：这一轮做的是
"网格干不干净"，用户很容易把"没有畸形单元"读成"结果可信"。少写这一句，
这个功能就会变成一种新的误导。

### 20.6 端点与前端

端点 `GET /api/mesh-quality?filename=`（路由器级依赖 `require_user`，未登录 401）：

| 情况 | 状态码 | 为什么 |
|---|---|---|
| 文件名不合法 | 400 | 与其它端点一致，路径穿越在这里挡住 |
| 几何文件不存在 | 404 | "文件不在了" |
| 还没生成网格（无 `.msh`） | 409 | 不是错误，是"顺序不对"：先 `POST /api/generate-mesh` |

前端分两块：`frontend/utils/meshQuality.ts`（纯函数，能被 node 单独执行）
和 `frontend/components/MeshQualityPanel.tsx`（只负责画）。三个刻意的取舍：

1. **摘要先给最小值**：判断网格能不能用看的是最差的那个单元，平均值好看完全
   可能由几个刀片单元之外的东西撑着；
2. **404 / 409 静默**（不显示面板）而不报红：它们表示"还没有网格"，是正常状态，
   报错会把用户引向一个不存在的问题；
3. **换几何时清空质量**：不清掉的话会显示"新零件 + 旧网格的直方图"，那是
   最容易被当成真的假信息。

还有一个**过期响应**问题：连续改网格尺寸会发出多个请求，先发的可能后到，于是
界面显示的是已经不存在的那个网格的质量——数字看着完全正常。用一个自增请求号
丢弃过期响应解决。

### 20.7 测试夹具的教训：不要用 C++ 绑定的调用约定搭夹具

第一版 `.msh` 夹具用 `gmsh.model.mesh.addNodes / addElements` 现搭一个网格，
结果撞在 `addElements` 的参数约定上（`nodeTags` 必须是**扁平**列表，传
`[[1,2,3,4]]` 会报 `object of type 'int' has no len()`），测试因为与业务无关的
原因失败。

改成**手写 MSH 2.2 文本文件**：人可读、可核对、版本稳定，而且仍然走完整的
`load_tet_mesh_from_msh` 读取路径。同时把第二个单元的节点顺序**故意写反**，
这样这条测试才真正钉住"朝向修正"那段代码——否则它只是把数组断言又重复了一遍。

再补一条：夹具本身要先被验证有效。测试里先断言"文件里那个反序单元的有符号
体积确实是负的"，否则"朝向被修正了"这条断言会变成空转（修正函数没跑也通过）。

### 20.8 我自己给 verify 埋的一个副作用

verify 里新加的检查调了 `POST /api/generate-cube` 来确保 `default_cube.step`
存在。但这个文件**被 git 跟踪**，而 STEP 里带时间戳——于是每跑一次 verify，
工作区就脏一次，提交里还会混进一个"几何好像变了"的二进制 diff。

改成"只有 metadata 返回非 200 时才生成"（新克隆的仓库本来就有这个文件）。
顺带把 verify 的输出日志从仓库根目录挪到临时目录——我一开始把
`.dev-verify.txt` 写在了仓库根，它不在 `.gitignore` 里，很容易被误提交。

**教训：任何"为了验证而调用的写接口"，都要先问一句"它会改动什么东西"。**

### 20.9 工具坑：`Get-Content` 对中文路径给出的行数是错的

`(Get-Content 'docs\03-修复记录.md').Count` 报 **891**，而 Python 数出来是
**1253** 行、1253 个 LF、0 个 CRLF。文件本身没问题（无 BOM、无 CR、无乱码名
文件），是 PowerShell 那一边的计数不可信。原因没有查明，但结论可用：
**在这个仓库里数行数/看内容，用文件工具或 Python，不要用 `Get-Content` 配中文路径。**

## 二十一、第十八轮：收敛阶基准（"我们究竟能不能测出收敛阶"）

### 21.1 为什么先做基准，而不是先做"用户模型的加密检查"

上一轮做完了网格**形状**质量，剩下的那一半是"够不够细"。最直觉的做法是：
拿用户的几何与边界条件，逐级加密、再求解，看结果是否稳定。

但这一步有个前提：**我们得先能确定地量出一个收敛阶**。如果连一个精确解已知
的问题都测不出理论阶数，那么对用户模型给出的任何"已收敛"都是空话——两次数
值接近，可能是因为收敛，也可能是因为两处都错得一样。

所以本轮先做两件事：

1. **收敛阶的度量与判定**（纯函数）：给一串随加密变化的数值，算相邻差值、
   用 Richardson 外推估计阶数 `p` 与极限值，并给出结论；
2. **制造解基准**：一个**精确解已知**的问题，逐级加密、测**真实误差**，
   看观测阶是否等于理论阶。

### 21.2 制造解为什么取二次函数，而不是线性

取 `T = x² − y²`。它在三维里是**调和函数**（ΔT = 2 − 2 + 0 = 0），因此是
`∇·(k∇T) = 0` 的精确解，可以直接用现有的热传导算子算。

关键是它**不属于 P1 单元空间**。如果图省事取线性解（比如 `T = x`），有限元解
会**逐节点精确**，误差恒在 1e-16 量级——于是每一级"误差"都相同，看起来完美
收敛，实际上什么都测不出来。`tests/test_convergence.py` 里专门有一条断言
把这个陷阱钉死：**误差必须明显大于机器精度**（L2 > 1e-4）。

### 21.3 实测结果

考察量是**真实误差**（对精确解），因此"外推极限趋于 0"本身就是一条强断言。

| 网格来源 | 级数 | L2 误差 | L2 阶 | H1 误差 | H1 阶 |
|---|---|---|---|---|---|
| 结构化（`MeshTet.init_tensor`） | n=4,8,16,32 | 4.891e-3 → 7.642e-5 | **2.000000000000** | 2.041e-1 → 2.552e-2 | **1.000000000000** |
| 真实流水线（gmsh → 本项目加载器） | mesh_size 2.5→0.3125 | 27.01 → 0.534 | **1.928** | 74.70 → 11.01 | **0.999** |

结构化网格自相似，误差比值**恰好**是 4.0000 / 2.0000，所以断言可以写到
`places=9`（不是"大概二阶"，而是"就是二阶"）。

两种网格来源回答的是**两个不同的问题**，这也是刻意分开的：

- 结构化 ⇒ 检验**离散格式的阶数**和**我们量阶数的方法**对不对；
- 真实流水线 ⇒ 检验**我们自己的网格读写有没有破坏收敛性**。上一轮那个
  `edge_lengths` 漏转置的 bug 正是出在这条路径上。

### 21.4 一个陷阱：阶数只用最后两级差值估计，所以不能截短序列

第一版让 `pipeline` 模式也接受 `levels` 参数。跑 3 级（2.5 / 1.25 / 0.625）
时 H1 阶只有 **0.68**，判定差点被判成"没收敛"；补上第 4 级（0.3125）后升到
**0.999**。

原因是 Richardson 估计只用最后两级差值，而 **H1 误差进入渐近区比 L2 慢**：
最细的一级还带着明显的更高阶项。所以"少跑一级"不是"少一点精度"，而是
**换了一个完全不同的问题**。

改法：流水线模式**固定跑完整序列**，不接受截短；`levels` 只对结构化模式生效。
理由写在代码注释里。这也解释了为什么第一版的容差必须放到 0.60 才勉强通过
——那不是"网格质量差"，而是序列选错了。

### 21.5 诚实的边界：基准覆盖了什么，没覆盖什么

第一版基准自己写了一遍 `asm(laplace, basis)`。那是**测了一个副本**——副本对了
不能证明生产代码对。所以把装配抽到 `thermal.assemble_conductivity`，
`solve_thermal_impl` 与基准**共用同一份实现**（改动只有一行，见 `thermal.py`）。

但**没有**覆盖的是：`solve_thermal_impl` 的"面 → 节点"Dirichlet 映射。
制造解的边界值在面上是**变化**的（`T = x² − y²`），而当前的 BC 模型只支持
"每个面一个常数温度"。所以：

| 环节 | 由谁覆盖 |
|---|---|
| 算子装配 | ✅ 本基准（与生产代码共用） |
| 求解 | ✅ 本基准 |
| 网格读写（gmsh → 本项目加载器） | ✅ 本基准的 pipeline 模式 |
| 面 → 节点的 Dirichlet 映射 | `tests/test_thermal.py` 的解析解断言 |

这条边界写进了接口响应的 `notes` 里，而不是只写在文档里——因为看结果的人
未必会去翻文档。要让生产求解器本身也支持制造解验证，需要给 BC 模型加
"空间变化的 Dirichlet"，那是后续的事。

### 21.6 判定逻辑：先看"能不能判"，再看"对不对"

`assess()` 的判定顺序是刻意的：

1. 级数不足 3 → "至少需要 3 级才能估计收敛阶"；
2. 最后两级完全相同 → "已达机器精度"（比收敛更好，但**不说阶数**）；
3. 序列上下跳动 → "没有朝一个方向收敛"（此时算出的 log 比值只是两个随机数
   之比，报出来会显得很专业但毫无意义）；
4. 差值**没有变小** → "尚未进入收敛区"，而不是报一个 0 或负数的阶数
   （负数会让人以为"阶数是负的"，真实含义是"还没收敛"）；
5. 阶数与理论值差太远 → 单独一句"不是按理论阶数在收敛"。

第 4 与第 5 条必须分开：**"网格不够细"要继续加密，"阶数不对"说明格式或实现
有问题**——两者的处理方式完全不同，混成一句会把人引向错误的方向。

### 21.7 又一次"我的测试写错了"

这一轮 36 个测试第一次跑挂了 3 个，**全部是测试期望写错，不是模块错**：

1. `assertAlmostEqual` 收到形状 `(1,)` 的数组 → 在 `round()` 上抛
   `TypeError`（用 `.item()` 取标量）；
2. 相对变化的阈值我随手写了个 `1e-4`，实际算出来是 `1.0002e-4`——差一点点；
3. "只用末三级"那条，我预期的公式是乱写的。构造的序列 `[1000,100,10,4,1]`
   里，末三级给出的阶数**正好是 1.0**（前两级会是 3.32），所以断言应当直接
   写 1.0，并顺便断言前两级给的是 3.32——那才真正证明了"只看末三级"。

这已经是第四次了。规律很清楚：**错的是我对数字的预期，不是代码**。所以现在
的习惯是——测试挂掉时先手算一遍期望值，再怀疑实现。

### 21.8 verify 里这一组检查的排位是有意的

收敛基准放在 `5/7 求解器物理校准` 的**第一条**，排在支反力守恒、热流解析对照、
模态频率之前。理由：如果离散格式本身不按理论阶收敛，后面那些"物理量对得上"
的断言都可能只是碰巧对上了。先确认底层的数值行为正确，再确认物理量正确。

## 二十二、第十九轮：对用户模型做 h-收敛检查

### 22.1 上一轮与这一轮的分工

| | `convergence.py`（上一轮） | `convergence_study.py`（本轮） |
|---|---|---|
| 对象 | 制造解（**精确解已知**） | **用户自己的模型**（没有精确解） |
| 量的是 | **真实误差** | 逐级之间的**差值**（自收敛） |
| 回答 | "这套离散会不会收敛、阶数对不对" | "这个模型的结果稳不稳定" |

两者缺一不可：格式收敛不等于你的网格够细；而自收敛的结论只有在格式本身
收敛的前提下才有意义。

### 22.2 自收敛能证明什么，以及**不能**证明什么

能：该量随加密单调趋稳、差值在缩小、可以估阶并外推。
**不能：极限就是真解。** 建模错误（材料、约束、载荷方向弄错）会收敛到一个
**错误的稳定值**——那类错误不会随加密消失。

所以接口响应的 `notes` 里**永远**带着这一句，而不是只写在文档里。理由和
上一轮一样：看结果的人未必去翻文档，而"收敛了 = 结果可信"是最容易产生的
误读。

### 22.3 本轮踩到的坑：gmsh 并不按名义尺寸成比例加密

第一版直接假设"网格尺寸减半 ⇒ 加密比 2"，于是用 `log(r)/log(2)` 估阶。
实测数据打了脸：

| 名义 `mesh_size` | 3.0 | 1.5 | 0.75 | 0.375 |
|---|---|---|---|---|
| 实测单元数 | 426 | 1366 | 9462 | 66837 |
| 折算平均单元尺寸 `N^(-1/3)` | 0.1328 | 0.0902 | 0.0473 | 0.0246 |
| **实际加密比** | — | **1.47** | **1.91** | **1.92** |

第一段只有 1.47 倍。后果是两层的：阶数算错，而且 `assess()` 里"差值必须
变小"这个判据**在前几级会失效**——第一段加密太浅，第二段加密更深，于是
差值反而变大（10.78 → 15.85），一个**完全正常**的模型被判成"未进入收敛区"。

这个 bug 很危险，因为它的表现是"工具说你的模型有问题"，而模型其实没问题。

修法两步：

1. **用实测尺寸估阶**：新增 `generalized_order(values, sizes)`，解
   ```
   (h1^p − h2^p) / (h2^p − h3^p) = |Δ1| / |Δ2|
   ```
   （二分法；`f` 关于 `p` 单调递增，所以解唯一）。加密比均匀时它**退化为**
   常用的 `p = log(r)/log(q)`，所以不是另一套东西，而是它的正确推广。
   无解时返回 `None`，含义是"**没有任何正的阶数能解释这组数据**"——比报一个
   负数诚实。
2. **把实测加密比报出来**：结论说明里必须写出各级单元数与实际加密比，
   否则用户看到"差值没变小"只会怀疑自己的模型。

还有一个相关修正：`levels` 的默认值从 3 改成 4。实测同一算例 3 级判
"未进入收敛区"，补到 4 级就正常了——**3 级经常不够**，这是数据说的，
不是猜的。

### 22.4 为什么"差值没有变小"的措辞必须列三种原因

第一版只写了"请检查是否存在应力奇异"。但差值不变小的原因至少有三类，
处理方式完全不同：

1. 还停在前渐近区（起始网格太粗 / 级数不够）——**继续加密**；
2. 该量本身不收敛（应力奇异：尖角、点载荷、单点约束）——**加密无用**，
   真值本身无穷大；
3. 各级网格并没有按预期幅度加密（见 22.3）——**先修网格序列**。

只提第 2 条会把用户引向"我的模型有奇异"这个错误方向，或者让他白加密很久。
所以现在的措辞明确列出三种可能，并附上实测加密比供判断。

### 22.5 四态结论，而不是"收敛/不收敛"

`status` 有四个值，刻意区分开：

| 状态 | 含义 | 该做什么 |
|---|---|---|
| `converged` | 都在收敛区，且主考察量最后一级变化小于阈值（默认 5%） | 可以用 |
| `marginal` | 都在单调趋稳，但变化幅度仍大于阈值 | 定性比较可以；要更稳继续加密 |
| `not-converged` | 有考察量的差值变化无法用正的阶数解释 | 看 22.4 的三条原因 |
| `insufficient` | 级数不足（<3 级，或单元数超上限） | **不做任何收敛判断** |

`insufficient` 时 `assessments` 是**空的**，而不是硬给一个结论：两级结果接近
可能是收敛，也可能是两处都错得一样。这是本功能最容易犯的错，所以单独
写了测试钉住。

阈值默认 5% 也是踩出来的：一开始定 2%，结果几乎所有 3 级检查都落进
`marginal`。原因是**收敛序列的最后一级变化大致就等于剩余误差本身**，
想让它降到 2% 以下等于要求剩余误差只有量值的 2%，3~4 级网格基本达不到。
实测 4 级时最大应力最后一级仍变化 19%。

### 22.6 不留痕迹（前两轮的教训）

网格一律划在几何的**临时副本**（`conv_<8位随机>.<原扩展名>`）上，用完在
`finally` 里删除副本和它的 `.msh`。理由：直接对用户的几何划网格会覆盖
`<几何名>.msh`，而那正是他当前在用的网格。

测试里有两条专门钉这个：临时文件必须删干净；`test_part.step` 与
`test_part.step.msh` 的**修改时间与大小**必须不变。verify 里也有一条查
`uploads/conv_*` 是否残留。

### 22.7 单元数上限要在**划之前**预判

收敛检查要跑 3~4 级，单元数按 h³ 涨。第一版只在划完网格之后检查单元数，
超了就停——但那一级已经划完了（已经花掉了时间）。

改成两步：划完当前级后，用 `N_next ≈ N_now · (h_now/h_next)³` **预测**
下一级；预计超上限就不划了，直接停并说明。另外级数上限 4 级、单级上限
20 万单元，都是硬限制而不是"建议"。

### 22.8 又是同一个语法错误（第三次）

这一轮我在 `convergence.py` / `convergence_study.py` 里**三次**把 ASCII
双引号嵌进双引号字符串（`"此时"差值必须变小"这个判据…"`）。中文语境下
这些引号看着毫无问题，但它是 Python 语法错误。

前两次靠 `ast.parse` 当场发现；第三次是加了一段中文说明之后。教训是：
**中文说明里的引号一律用「」**，而"改完立刻 `ast.parse` 一遍"这件事
不能省——因为新建的文件如果暂时没有被任何模块 import，语法错误要等到
运行到它的时候才暴露。

为此加了一个顺手工具：对仓库里每个 `.py` 跑一次 `ast.parse`（43 个文件，
不到一秒），在提交前跑。

## 二十三、第二十轮：收敛检查的前端接线

### 23.1 先把"配置"抽出来，而不是复制一遍

界面要新加一个"跑收敛检查"的按钮，它发出的请求体与"跑一次求解"**几乎**一样
（几何、材料、边界条件、面元数据、长度单位、模态阶数）。最省事的做法是把
那段组装代码复制到新函数里。

没有那样做。原因很具体：**收敛检查的全部意义就在于"各级之间只有网格不同"**。
两处各写一套的话，将来任何一次改动（加一个单位、改一次温度换算、多一个
求解参数）都可能只改到其中一处，于是收敛检查悄悄算的是**另一个问题**——
而它的结论照样会打印得头头是道。

所以抽成 `buildSolverSetup()`，两处共用。改动是纯搬运（搬运后 `handleSolve`
里的 `validBCs` + `requestBody` 构造整段删除，改为一次调用 + 空值保护），
diff 里能直接对照。

### 23.2 趋势图的横轴方向写反了（被自己的自检抓到）

面板上画的是"考察量随 h 的变化"，横轴标注"粗 → 细"。第一版的实现是：

```ts
const logH = points.map(p => -Math.log(p.elements) / 3);   // 网格越粗，这个值越大
points[i].x = (logH[i] - xMin) / (xMax - xMin);            // 结果：最粗的画在了右边
```

`-ln(N)/3` 随网格变粗而**变大**，所以直接归一化会把最粗的网格放到 `x = 1`。
自检实测给出的横轴是 `1.000, 0.770, 0.387, 0.000`——与界面标注正好相反。

修正就是把映射反过来：`x = (xMax - logH) / (xMax - xMin)`。

顺带发现**我的断言写弱了**：原来那条"横轴按单元数（不是按第几级）排列"
只检查 `x` 递增，而"按级数下标归一化"同样是递增的——**它根本区分不出这两种
实现**。改成检查"横轴不等距"（各级实际加密幅度并不相等，第二个点按单元数算
是 0.230，按级数下标算是 0.333，用阈值 0.05 区分开）。这才算真的钉住了。

### 23.3 又是两个我自己算错的期望值

自检第一次跑挂了 4 条：2 条是实现的问题（见 23.2），另 2 条是**我把数字
算错了**：

- `373.15` 保留 4 位有效数字是 `373.1`，我写成了 `373.2`
  （`373.15` 的双精度表示其实是 `373.14999…`，所以不进位）；
- `1.084e-9 m` 换算成毫米是 `1.08e-6 mm`，我写成了 `1.084 mm`
  （把 `1e-9 m` 当成了 `1 mm` 量级）。

规律每次都一样：**测试挂掉时先手算一遍期望值，再怀疑实现**。这次两条恰好
一个真 bug、一个我的错——所以"先手算"不是不怀疑实现，而是把两者分开验。

### 23.4 前端这一层为什么也值得写自检

`frontend/utils/convergenceStudy.ts` 里的东西看着没什么技术含量（映射字段、
格式化数字、算几个归一化坐标），但它有三类错误**都不会报错**：

1. **字段名对不上**（后端 `last_relative_change` vs 前端 `lastRelativeChange`）
   ——静默地少显示一项，用户以为"这一项本来就没有"；
2. **把缺失显示成 0**——本项目吃过一次亏（`formatFrequency(null)` 返回
   `'0 Hz'`，把"数据缺失"显示成"刚体模态"）。收敛检查里的 0 是有意义的
   （"最后一级变化 0%"），所以必须把两者分开；
3. **把四态压成两种颜色**——`marginal`（在趋稳但没到阈值）既不是通过也不是
   失败，而它**恰恰是最常见的状态**。压成绿/红会误导用户。

所以这块逻辑和网格质量、模态一样：纯函数 + node 直接执行 + verify 自检，
再加一条"拿**后端真实响应**喂给前端解析"的契约检查（字段改名只有这条能抓到）。

### 23.5 一个原则：结论里的限定在界面上必须能读到

后端返回的 `notes`（"自收敛不能证明模型正确"、"应力奇异加密无用"、
"网格划在临时副本上"）在面板里做成**可折叠但默认存在**的一块，而不是丢掉。
可以折叠是为了不占地方；不能省略是因为**看结果的人未必去翻文档**，
而"收敛了 = 结果可信"是最容易产生的误读。

### 23.6 顺带记一个操作坑：`verify` 会因为服务没起来而整段失败

中途服务被停掉了（`backend DOWN`），`verify` 直接 `EXIT=1`——这是**正确**的
行为，但输出里第一眼只看得到"失败"，容易误以为是代码的问题。所以现在跑
`verify` 之前先探一次 `/api/health` 和前端首页，确认服务在跑再看结果。

## 二十四、第二十一轮：结果导出（CSV / VTK）

### 24.1 为什么"导出"排在"剖切面/动画"前面

"结果后处理"这一项列了很多东西：剖切面、等值面、变形动画、导出、报告。
这一轮只做了**导出**，而且是刻意的——理由是**验证性**：

导出有一条可以精确钉住的契约：**文件里的数值必须与求解结果逐位一致**。
这一条能用两种互相独立的方式验证（前端文本断言 + Python 读回比对），
而"剖切面好不好看"没有任何判据。所以先把"数据能带出去"这件事做对，
再谈好不好看。

这对"可协作、能长期推进"也更实在：结果能离开这个工具，别人才能核对、
才能存档、才能写进报告。

### 24.2 数据本来就在浏览器里，所以导出写在前端

求解结果已经在浏览器内存中（`meshData`），导出只是把数组写成文本。
没有加后端 `/export` 端点，因为那样：要多一次往返、要把结果重新传回服务端、
而且会把"结果在内存里、重启即丢"这个既有限制扩散成"导出也一起丢"。

所以 `frontend/utils/resultExport.ts` 是纯函数，界面只负责 Blob + 触发下载
这段必须依赖浏览器的胶水。

### 24.3 精度：用 `String(x)`，不用 `toFixed`

JavaScript 的 `String(0.1)` 给出**最短且能精确还原**的表示（与 Python 的
`repr` 同源算法），所以 `Number(String(x)) === x` 对任意双精度数成立。

写成 `toFixed(6)` 会**静默丢精度**——文件看着完全正常，数值已经不对了。
这正是最难发现的一类错误，所以自检里直接钉两条：

- 正向：`Number(写出来的文本) === 原始值`（含 `0.1`、`1/3`、`1e-300`、`5e-324`）；
- 反向：`Number((1.2345678901234567e7).toFixed(6)) !== 1.2345678901234567e7`，
  证明"不用 toFixed"这个选择不是随便定的。

### 24.4 跨语言往返：这一轮最强的证据

verify 里新增的检查是这样的：

```
POST /api/solve 的真实结果（832 节点 / 2735 单元）
   -> 交给 node 执行前端的导出纯函数，写出 result.csv 与 result.vtk
   -> 用 Python **手写解析** 把两个文件读回来
   -> 与求解结果逐位比对：坐标、位移、应力、单元连接
```

实测输出：

```
[PASS] 结果导出（真实结果 -> CSV/VTK -> Python 读回逐位比对）
       832 节点 / 2735 单元，坐标·位移·应力在 CSV 与 VTK 两个文件里都与求解结果逐位一致
```

**VTK 的解析是手写的**，没有引入 vtk 库。这不是省事，而是刻意的：用一个宽容
的库来读会把格式错误掩盖掉，而手写解析对格式的要求更硬（段名、计数、
"每行 4 + 四个索引"、`CELL_TYPES` 必须是 10、`SCALARS` 后面必须有
`LOOKUP_TABLE` 行）。这样"我们的文件确实是合法 VTK"才算真的验过。

同时它还顺带验了**两条独立路径写同一份数据的一致性**：CSV 与 VTK 是两段
不同的代码生成的，检查里额外断言"同一个节点在两个文件里的位移相同"。

### 24.5 不自洽时**拒绝导出**，而不是生成一个看着正常的文件

如果场的长度与节点数对不上，导出的文件会**错位**——位移被贴到别的节点上，
而文件本身完全合法、能被 ParaView 打开、看起来就是一张云图。这是最坏的
一类错误：没有任何报错，只有错误的结论。

所以 `validateExportMesh` / `validateExportFields` 会检查：

- 节点坐标与向量必须是有限数（`NaN` / `Infinity` 在 CSV/VTK 里都没有合法写法）；
- 单元索引必须是整数且落在节点范围内；
- 每个场（标量或矢量）的长度必须等于节点数。

任一不满足就返回 `null`，界面提示原因，**不生成半张表**。

### 24.6 两个小决定，都有原因

- **行尾**：CSV 用 `\r\n`（RFC 4180，Excel 在 Windows 上对 LF 的兼容性时好时坏），
  VTK 用 `\n`（ParaView 两种都认，而 LF 便于在 Git 里看 diff）。
  测试把两者都钉住了，免得以后有人"顺手统一"成一个而不知道原因。
- **列名自带单位**：`displacement_m`、`von_mises_Pa`、`temperature_K`。
  导出文件最常见的用途就是给别人看，而"这个数是米还是毫米"必须写在文件里。
  反过来，模态振型是**归一化的无量纲相对量**，列名里就**不能**带单位——
  带上会让人把幅值读成真实位移。

### 24.7 界面上只列真的能用的按钮

导出按钮只在**真有可导出的结果**时出现（`hasExportableResult`）。
列一个点了会弹"无法导出：请先求解"的按钮没有意义——那种交互只会教用户
忽略提示。

## 二十五、第二十二轮：求解记录（run history）

### 25.1 它补的是"协作"缺的那一块

在此之前，被共享的人（viewer）打开项目只能看到**配置**，看不到属主算出来的
任何数值——求解结果留在属主的浏览器内存里，刷新就没。于是"共享"实际上只能
共享"准备做什么"，不能共享"做出了什么"。

求解记录把"跑过哪些算例、各自什么网格、结果多少"落到后端，读权限就能看。

### 25.2 只存摘要，不存完整场——这是刻意的

位移/应力场是逐节点的数组，中等模型的 JSON 就有几 MB。存进 SQLite 会让数据库
迅速膨胀，而"长期可维护"里很大一部分就是**数据不要无限长**。

所以只存标量摘要（最大应力、最大位移……）+ 网格信息；完整数据由导出功能带走
（CSV / VTK，见第二十一轮）。每个项目上限 `MAX_RUNS_PER_PROJECT = 50` 条，
超出按时间裁掉最旧——**不设上限的表**是那种"两年后才被发现"的问题。

### 25.3 一个取舍：不让前端把整个结果传上来

最自然的做法是"前端把求解结果 POST 上来，后端提取摘要"。没有那样做：那些
数组是 MB 级的，而求解任务刚刚才把它传给浏览器，为了记几个数再回传一遍是纯
浪费。所以前端只提交它已经拿到的标量。

代价是"哪个字段是最大应力"这套规则在两侧各有一份。用两道闸门防止漂移：

1. `RUN_QUANTITIES` 显式声明每种分析类型允许的键，**多余或缺失一律 400**——
   拼错的字段不会被静默存下来（那会变成"历史里这一项一直是空的"，没人知道
   为什么）；
2. `tests/test_runs.py` 断言这份声明与 `convergence_study.extract_quantities`
   的键集合完全一致。不能共用代码时，至少让漂移立刻失败。

### 25.4 `NaN` 不是合法 JSON——必须在写入时挡住

摘要要序列化成 JSON 存库。Python 的 `json.dumps(float('nan'))` 会写出 `NaN`，
自己的 `json.loads` 也读得回来，**但浏览器的 `JSON.parse` 会直接抛错**：
整个历史列表都打不开，而库里的数据看起来完全正常。

所以校验在写入时就把非有限值拒掉（400），而不是等某个用户的浏览器白屏。

顺带还有一条：`True` 在 Python 里是 `int`，但 `max_stress: true` 不该被当成
1.0 记下来——所以 `_finite` 显式排除 bool。

### 25.5 坏数据要**逐条**隔离，不能整份失败

库里那条 JSON 坏了（例如有人手工改过库）时，后端只把这一条降级成空摘要并
带上 `summary_parse_error`，其余记录照常返回；界面把这一条标成"摘要已损坏"。

整份列表打不开是最坏的结果——用户会以为"记录全丢了"，而那正是他最需要看到的
证据。这与前端侧"坏记录逐条丢弃"是同一条原则（`toRunList`）。

### 25.6 权限：三处状态码刻意不同

| 操作 | 要求 | 无权时 | 只读时 |
|---|---|---|---|
| 看记录 | `can_read` | 404 | — |
| 记一条 | `can_edit` | 404 | **403** |
| 删一条 | `can_edit` | 404 | **403** |

与项目共享那一轮的理由一致：**无权访问的人不该知道项目存在（404）；已经能
看见项目、只是不能写的人，返回 404 只会让他困惑（403）**。无主项目（`unowned`）
可见但不可写，提示里直接写"认领前"。

删除还额外按项目校验归属（`delete(run_id, project_id=...)`）：否则知道一个
run id 就能删掉任意项目里的记录。

### 25.7 踩到的坑：`from X import f` 在导入时绑定

测试第一版整片失败，全是 404 —— 因为 `runs.py` 里写的是
`from project_store import get_store`，而测试只替换了 `projects_module.get_store`。
**`from X import f` 是在导入时把函数对象绑进来的**，每个模块各持一份引用，
`runs_module.get_store` 仍然指向真实库（表现成"项目不存在 → 404"，
很容易误判成权限逻辑写错）。

修法是在测试里逐个替换四份绑定，并把原因写进注释——这类"看起来像业务 bug 的
测试装置问题"最费时间。

### 25.8 删除项目要级联清掉记录

否则会留下**再也无人能访问**的孤儿行：记录端点的第一步就是查项目权限，
项目没了永远是 404，那些行只会一直占空间。

### 25.9 界面：空历史是一句正常的话

"这个项目还没有求解记录。跑一次求解后会自动记下来。"——不是错误、不报红。
一个还没跑过求解的项目是完全正常的状态，报红会让人以为功能坏了。

另外：记录里的数值复用收敛检查那张单位表与格式化函数
（`convergenceStudy.formatQuantity`），所以同一个量在两个面板里显示成同一个数。
为此给 `quantityLabel` 加了本地兜底标签表——没有后端 `labels` 时（记录这条
路径）也不会把英文键名丢给用户。这个改动被 `convergenceStudy` 自己的自检
当场抓到（它断言过"没有数据时也能取标签"），断言随之更新。

## 二十六、第二十三轮：跨运行对比（"这几次运行收敛了吗"）

### 26.1 先解决"能不能比"的问题

上一轮把"跑过哪些算例、结果多少"存了下来。有了几条记录之后，最自然的问题是：
**同一套配置下加密网格，结果收敛了吗？**

但这个问题有个前提：只有**配置相同、只有网格不同**的几次运行才构成一条收敛
序列。材料变了、边界条件改了、几何换了，数值的变化就跟网格无关——把它们混在
一起算"收敛阶"，数字看着很专业，其实是编出来的。

所以本轮先加一个**配置签名**（`setup_signature`）：前端提交运行记录时带上
`setupSignature`（复用已有的 `setupSignature(buildSetupPayload(...))`），
后端只当**不透明字符串**存。跨运行对比时按 `(分析类型, 签名)` 分组，
**不同签名绝不混成一条序列**。

没有签名的旧记录（本功能上线前的数据）会被放进 `comparable=false` 的组：
**照实显示、但拒绝判定**，并说明原因。"猜它们配置应该一样"是不可接受的。

### 26.2 一个真 bug：我把"从粗到细"排反了

第一版拿**单元数**当排序键并降序排，同时用它算 `h = N^(-1/3)`。问题是：

- 单元数**越大**网格越**细**，所以"按单元数降序"是**细 → 粗**，方向反了；
- 于是传给 `generalized_order` 的尺寸序列是**递增**的，而它要求严格递减，
  只能返回 `None` —— 表现成"无法判断"，而不是一个明显的错误。

更隐蔽的是**两种来源的单调方向相反**：单元数越大越细，而名义网格尺寸越大
越粗。第一版把它们当成同一个键用。修法是抽一个 `_mesh_measures(summary)`
返回 `(fineness, h)`，让"细度"的含义在两种来源下一致（没有单元数时用
`1/尺寸`），排序与估阶都从它出发。

测试当场抓到了（`TypeError: NoneType - float`），但**我的测试期望也写反了**
——我照着实现的错误方向写了断言。所以修的时候要判断"哪一边错了"，
而不是让断言去迁就实现。

### 26.3 顺带加固的几件小事

- **同一个网格跑两次只算一次**（保留最新）：重复的尺寸不是一次加密，
  留着会让密序不严格递减、判定直接失效，而用户只是把同一件事跑了两遍。
- **缺网格或缺数值的记录跳过**，但不会让整组失败。
- 结论里写明"**【事后对比，不是受控加密实验】**"：这些运行是用户按自己的
  节奏跑的，不是我们安排的加密序列，顺序与倍数都不受控。
- `setup_signature` 是**加列迁移**（SQLite 没有 `ADD COLUMN IF NOT EXISTS`，
  基类用 `PRAGMA table_info` 先查再加）。专门写了一条测试：**按老结构建库**、
  再打开新的 `RunStore`，验证补列生效且老记录读得回来——开发机和别人的机器
  上都已经有旧库了，这比"新库能用"重要得多。

### 26.4 验证：让输出本身成为证据

verify 里这一组用**真按二阶收敛**的合成数据（`u = u* + C·N^(-2/3)`）走完整的
HTTP 路径，所以打印出来的观测阶本身就是证据：

```
[PASS] 跨运行对比：同签名的 3 次运行被判为二阶收敛
       观测阶=2.0 外推极限=70000000.0 （真值 7e+07）
[PASS] 跨运行对比：数值按粗 → 细单调且逐级更接近真值
       values=['7.03e+07', '7.008e+07', '7.002e+07']
```

**外推极限精确复原了真值 7e7**——这不是"能跑通"，是"算对了"。第一版这组数据
是我随手编的（1e7/2e7/4e7，差值在变大），打印出来是 `order=None`：检查能过，
但说不出任何有用的话。**用有解析答案的数据做端到端检查**这条，这次又赢了一次。

另外把"数值按粗 → 细排列"的断言从"递增"改成"单调且逐级更接近真值"：
后者才是真正想说的话，而且不依赖我从上方还是下方趋近这个细节。

### 26.5 前端的取舍

- 对比结果和记录列表**一起取**，但对比失败**不影响列表显示**——列表是有用的，
  对比是附加信息。
- 只有 1 个网格的组不显示（那就是列表里的一条，没有对比价值）；
  但 `comparable=false` 的组**要显示**——那是必须如实告诉用户的事。
- 坏组逐条丢弃（`toRunAnalysis`），与 `toRunList` 同一条原则。

## 二十七、第二十四轮：剖切面（clipping plane）

### 27.1 先说清楚这一轮**验不到**什么

"把零件切开看内部"里，**只有几何是可以精确验证的**：平面方程、包围盒、
以及在给定平面下有多少节点被剖掉——全是闭式可算的。

而"剖开之后屏幕上确实切开了"**没有**任何自动化判据（我也没有截图能力）。
所以这一轮的诚实说法是：

| 环节 | 谁负责 |
|---|---|
| 包围盒、平面方程与符号方向、节点分类 | ✅ `frontend/utils/clipPlane.ts` 纯函数 + node 自检（精确断言） |
| 平面接到材质上、渲染器开关 | ⚠️ 只有 `tsc` + `vite build` 通过，**视觉效果需在浏览器里看** |

把这条边界写在这里，而不是含混地说"实现了剖切"。

### 27.2 符号约定只换一次

three.js 的 `Plane.distanceToPoint(p) = normal · p + constant`，**距离 >= 0 的一侧
被保留**。本模块沿用同一形式，算出来的 `{normal, constant}` 原样喂给
`new THREE.Plane(...)`，中间**不再换第二套符号约定**。

理由很实际：这类符号约定换一次就够错一次，而错了的表现是"模型整个不见了"
——看起来像别的问题（相机、材质、几何），排查方向全是错的。所以自检里把
符号钉死：

- 保留小侧 ⇒ `normal = -x`、`constant = position`；
- 保留大侧 ⇒ `normal = +x`、`constant = -position`；
- 两侧距离互为相反数；
- 立方体正中切开 ⇒ **恰好 4 个节点**被保留（数得出来的值）。

### 27.3 不剖切时挂一个"模型外面的平面"，而不是不挂平面

three.js 的着色器程序缓存键里含剖切面**数量**。数量从 0 变 1 会触发着色器
重编译，而滑杆每拖一下就变一次——手感会明显变卡。

所以未启用时仍然挂**一个**平面，只是把它放在包围盒之外（`max + span`）。
数量恒为 1，永远不重编译；而"不剖切"这个语义仍然严格成立（自检里断言
`kept === 节点总数`）。

退化情形也顺手处理了：某一轴跨度为 0（平面模型）时，往外让开一个单位，
保证"未启用"真的一个节点都不切。

### 27.4 界面上报出"剖掉了多少"，而不只是画出来

面板里除了选轴/拖位置/切换保留侧，还会显示：

> 剖切 x = 0.5000，保留较小的一侧：留下 4 个节点、剖掉 4 个（保留 50.0%）

理由是：**光看画面，用户不知道截面在模型的哪个位置**（尤其模型不是立方体时）。
给出节点数与百分比，用户才能判断"我看到的这一刀切在哪儿"。这同时也是唯一
能自动化验证的那部分信息，所以它既对用户有用，也让这一轮有可验证的产出。

### 27.5 实现位置：几何在 Scene3D，生效在 ModelViewer

材质定义在 `ModelViewer` 里（`clippingPlanes` 是材质属性），而浮层 UI 在
`Scene3D` 里。第一版把几何计算写在了 `ModelViewer`（那里没有 `props`），
tsc 直接报了 17 个"找不到名字"。

修法：几何与状态留在 `Scene3D`（它持有 `meshData`），把算好的 `THREE.Plane`
作为**一个 prop** 传给 `ModelViewer`，由后者写进材质。两边只通过这一个 prop
对接，避免同一套平面算法写两遍。

## 二十八、第二十五轮：让 CI 真的跑"证据"，并用干净检出验证它

### 28.1 这一轮之前的真实状态

CI 里有两个 job：后端单元测试、前端类型检查与构建。而本项目的**主要证据**
——解析解物理校准（支反力守恒、热流 `q=kΔT/L`、模态刚体模态与二阶收敛、
制造解收敛阶、导出文件的 Python 回读逐位比对）——**全在 `verify` 里，
不在单元测试里**。也就是说：CI 从来没有跑过这套项目最看重的东西。

更根本的一层：`origin/main` 从未 push，所以 CI **一次都没在 GitHub 上执行过**。
"已验证"这句话因此只成立于开发者本机。

### 28.2 用"新鲜克隆"代替"我觉得应该能行"

`git clone` 到临时目录是最接近 CI 的复现方式：落下来的**只有被跟踪的文件**，
没有 venv、没有 `node_modules`、没有 `*.msh` 缓存。

第一次跑就抓到一个**真 bug**：

```
ERROR: test_user_mesh_is_not_disturbed
FileNotFoundError: ...\backend\uploads\test_part.step.msh
```

这条测试要验证"收敛检查不会覆盖用户自己的网格"，做法是记下 `.msh` 的
修改时间与大小再比对——但**它假定这个文件已经存在**。`*.msh` 是 gitignore 的
可再生产物，干净检出里没有，于是测试在 CI 上必然失败；而本机一直绿，因为
那些缓存早就生成了。

**这就是"只在本机验证"最典型的漏网方式：测试悄悄依赖了一个不进版本库的
生成物。** 修法是在测试里先确保网格存在（生成它），而不是跳过——跳过会让
这条断言在干净环境里静默消失，比失败更糟。

顺带得到一条便宜的本地复现方式，已写进 `CONTRIBUTING.md`：

```
python3 tools/tasks.py clean && python3 tools/tasks.py test
```

（`clean` 会删掉 `*.msh` 等可再生缓存。实测：clean 之后 481 个用例仍然全绿。）

### 28.3 CI 新增第三个 job：端到端验证

```
verify:
  env: GMSH_TERMINAL=0        # 否则 gmsh 的网格输出会把结论淹掉
  - pip install -r backend/requirements.txt
  - npm ci                    # verify 的 1/7 要跑 tsc
  - setup-node: '24'          # ★ verify 用 node 直接执行 .ts，需要 Node >= 23
  - 启动 uvicorn（nohup，写 ci-backend.log）+ 轮询 /api/health
  - python tools/tasks.py verify
  - if: failure() → tail -200 backend/ci-backend.log
```

几个刻意的决定：

- **与另两个 job 并行，不加 `needs`**：出问题时能一眼看出是单元测试挂了还是
  端到端挂了，也不用排队等；
- **启动后端与 `verify` 放在同一个 step 里**：跨 step 的后台进程能不能活下来
  取决于 runner 怎么处理进程组，放在一起就不必赌这件事；
- **Node 24 只装给这个 job**：`frontend` job 只做 tsc 与打包，Node 20 够用，
  但这个 job 不够——两处需求不同，就写两处。
- **失败时输出后端日志**：否则"verify 挂了"只能靠猜。

### 28.4 顺手修的文档漂移：加一道自动闸门

`CONTRIBUTING.md` 里长期写着 verify "**84** 项"，而实际早就过百（当时 133）。
我已经手工同步过好几次计数，每次都得在四份文档里找——这次不找补了，改成
**自动闸门**：`verify` 的最后一条检查会把文档里声明的"当前总数"与实测值比对，
不一致就列出**具体哪个文件写了什么**。

两个设计细节：

- **只匹配"当前总数"的固定措辞**，不匹配 `\d+ 项`：文档里有大量历史数字
  （"verify 新增 6 项"、"45 个用例、0.3 秒"），那些是当时的记录，不该等于今天的
  总数。规则写死在 `_DOC_COUNT_PATTERNS` 里，每个 pattern 绑一份文件。
- **用例数用"只收集不执行"的方式数**（`unittest.TestLoader().discover`），
  所以这个闸门不跑测试套件、代价近乎为零。

第一次运行立刻报出：`CONTRIBUTING.md 写的检查项数是 84，实际 134`。

### 28.5 验证

新鲜克隆里（借 `node_modules`，其余全是克隆自带内容；CI 用 `npm ci` 装）：

```
=== 从克隆启动后端（端口 8011）===
  后端已就绪：http://127.0.0.1:8011
=== 克隆里跑完整 verify ===
  PASS: 133  FAIL: 0        （当时 HEAD；修复后为 134）
```

这证明了一件此前只能靠断言的事：**端到端验证（含全部解析解物理校准）在一个
干净检出上是可以通过的**，不依赖开发机上的任何缓存。

## 二十九、第二十六轮：把"干净检出检查"做成项目里的一等公民

### 29.1 上一轮的那个脚本本来会消失

上一轮为了验证 CI 能不能在干净检出上跑通，我写了个一次性 Python 脚本放在临时
目录里，跑完就丢。它当时**第一次运行就抓到了一个真 bug**（测试依赖
`test_part.step.msh` 存在）。这种工具留在临时目录里等于没有——所以这一轮把它
变成 `python tools/tasks.py clone-verify`。

### 29.2 它做什么

```
git clone 到临时目录（只有被跟踪的文件）
  → 克隆里跑后端单元测试
  → 借来 frontend/node_modules（CI 对应 npm ci）
  → 从克隆启动后端（端口自动在 8011~8020 里挑）
  → 克隆里跑 verify（SIMCLOUD_API 指向那个端口）
  → 无论成败都终止后端、删掉临时目录（--keep 保留现场）
```

它防的是**只有本机能过**的那一类问题：克隆里没有 venv、没有 `node_modules`、
没有 `*.msh` 缓存，任何"悄悄依赖了不进版本库的生成物"的测试都会露出来。

### 29.3 三处刻意的设计

**先说清楚它测的是"已提交"的状态。** 克隆操作拿不到工作区里未提交的改动，
所以任务会先列出来：

```
工作区有 3 处未提交改动，**克隆里不会有它们**：
    tools/tasks.py
    backend/uploads/零件1.STEP
    …
（这正是这个任务要说明的事：它验证的是已提交状态的干净检出）
```

不写这句的话，"克隆里通过了"会被误读成"我刚写的代码通过了"——那正好是它要
防的那种错觉。

**借 node_modules 而不是复制。** 有了它，`verify` 的 1/7（`tsc` 类型检查）
能在克隆里跑，于是"前端源码在干净检出里能不能编译"也有了证据。用目录链接
（Windows 用 `mklink /J`，POSIX 用 `symlink`）：几十兆的依赖复制一遍既慢又
没必要。借不到就退化为 `--skip-frontend` 并明确警告。

**端口自动挑，且不与 `dev` 冲突。** `verify` 通过 `SIMCLOUD_API` 指向临时
后端，端口在 8011~8020 里探测一个空闲的，所以本机上跑着的开发服务完全不受
打扰——这一点上一轮已经验证过（临时后端用完即终止，8000/3000 上的服务照常）。

### 29.4 给"验证工具自己会不会撒谎"加一条检查

`clone-verify` 靠 `summarise_verify()` 解析 `verify` 的输出判断成败。这个解析
一旦写错（比如漏数 FAIL），它会**谎报成功**——一个验证工具谎报验证结果，是
这套体系里最坏的一种错误。

所以 `verify` 里加了一条针对它的检查，喂一段合成输出并断言统计结果：

```
[PASS] 验证输出解析（clone-verify 靠它判成败）     PASS=2 FAIL=1 failures=['乙  no']
```

顺带说明：这条检查的位置很关键——它必须在"文档计数闸门"**之前**，因为闸门
把"检查项总数"和文档里的声明比对，而总数包含它自己。

### 29.5 写这条任务时又踩了一个坑：`ast.parse` 不查名字

`clone-verify` 写完、本机 `verify` 135 项全过，我把它提交后跑了一次——**退出码 1**，
而输出里 135 项全是 PASS。原因：结尾的成功提示我写成了 `ok_msg(...)`，而这个
函数叫 `ok(...)`，直接 `NameError`。

值得记的是**为什么没被早发现**：`ast.parse` 只查语法，**不查名字解析**。一个
"调了不存在的函数"可以一路通过语法检查、通过导入、通过所有单元测试（因为没人
调用那条分支），在任务**跑完最后一步**时才炸。而 `tools/tasks.py` 恰恰是唯一
没有单元测试覆盖的文件。

于是加了一条闸门：**用 pyflakes 查 `tools/tasks.py` 的未定义名字与未使用导入**。

- 为什么只查这一个文件：它是唯一没有测试覆盖、且"未定义名字"代价最大的地方
  （每个任务都要把活干完才发现失败）。实测 `tools/tasks.py` 在 pyflakes 下**零
  告警**，所以这条闸门不会产生噪声。
- 为什么 pyflakes 是**可选**依赖：`tools/tasks.py` 刻意只用标准库（这样 CI 不必
  多装东西）。所以没装时这条检查跳过并在说明里写明；CI 会 `pip install pyflakes`，
  于是那条在 CI 上始终生效。
- 顺手清掉了它查出来的两处死导入（`convergence_study.py` 里我自己的
  `Callable` / `Field`）。`backend/*.py` 整体还有 32 条（多为未使用导入），
  这一轮没有扩大范围——把闸门做宽会把现有的噪声变成红色。

### 29.6 闸门当场抓到了我自己

加完这条闸门，`verify` 立刻红了：

```
[FAIL] 文档里的计数与实测一致    README.md 写的检查项数是 135，实际 136
```

原因是 README 里有**两处**检查项数声明，而我那个同步脚本用的是
`replace(old, new, 1)`（只替换第一处）。也就是说：上一轮加的自动闸门，**在
这一轮就抓到了我在几分钟前亲手引入的漂移**。这比任何"以后记得同步"的约定
都管用。

### 29.6 修完第一个又踩第二个：pyflakes **也**查不出的一类

把 `ok_msg` 改成 `ok` 之后再跑一次 `clone-verify`——**还是退出码 1**：

```
TypeError: 'bool' object is not callable
  File "tools/tasks.py", line 4755, in task_clone_verify
    ok("干净检出可以跑通：单元测试 + 端到端验证")
```

原因是我在这条任务开头写了 `ok = True`（成功标志），**遮住了模块级的 `ok()`
助手**。这一类 pyflakes **查不出来**——语法完全合法，名字解析也"有定义"，只是
定义错了地方。

于是又加了一道**只用标准库 `ast`** 的针对性检查：模块级的助手函数名不许在函数
体里被同名局部变量或参数覆盖。它不需要 pyflakes，因此任何环境都生效。用一段
合成代码验过它确实能抓到：

```
synthetic: (False, 'task_x() 里的 ok')
```

它同时照出**既有代码里的同类隐患**：9 个 `_check_*` 助手写着
`ok, detail = _run_node_module_selftest(...)`——`ok` 是局部名字，遮住了助手。
当前它们只是返回这个元组、不调用 `ok()`，所以没炸；但那就是同一颗雷。

既然闸门要严格，就把地雷拆掉而不是放宽规则：机械改名 15 处解包、14 处返回、
14 处条件表达式（`if ok else detail` → `if passed else detail`）。改完 verify 里
那些助手**全部仍被实际调用并通过**，等于顺手量了一遍改名没改坏。

两条都记在同一处：**验证工具报错不可怕，"用错误的退出码汇报成功"才可怕**——
它会让人以为干净检出通过了。

### 29.7 另一个反复踩到的操作坑

把带单引号的 Python 脚本塞进 PowerShell 的 `@'...'@` here-string：单引号会
**提前结束**字符串，脚本静默不执行——这次是改名脚本没跑，而我以为跑了（下一步
的检查结果没变才露出来）。照旧：非平凡脚本一律写成临时 `.py` 文件再执行。

### 29.8 验证

- 本机 verify：**137 项全部通过**（含两道新闸门、验证输出解析自检、文档计数
  闸门 `481 个用例 / 137 项检查`）；481 个后端用例通过。
- `clone-verify` 在已提交状态的干净检出上复验通过，退出码 0。
- 文档：README（命令清单 + 计数）、CONTRIBUTING（命令表 + 可选依赖 pyflakes）、
  CI（新增 `pip install pyflakes` 步骤）。

## 三十、第二十七轮：并发编辑不再静默覆盖

### 30.1 协作里最后一块"会静默出错"的地方

共享做完之后，属主和 editor 可以同时编辑同一个项目——而保存策略是"后保存的赢"。
这意味着**先保存的人的工作会无声消失**：没有报错、没有提示，他下次打开才发现
自己加的边界条件不见了。

这一轮不改这条架构（真正的实时协同是 OT/CRDT 那一档工程），只把失败模式从
**静默丢数据**换成**显式冲突**：保存时带上"我是基于哪一版改的"，期间有人改过
就拒绝而不是覆盖。

### 30.2 用版本号，不用锁

`projects` 表加一列 `setup_version`（加列迁移，老项目从 0 开始）。每次保存 +1。

- 带 `If-Match: "<版本>"` → 只在库里的版本与它相同时写入，否则 **409**；
- 不带这个头 → 无条件覆盖（老客户端 / 脚本的兼容路径）；
- 409 响应带 `ETag`（当前版本），客户端据此立刻重试或先看差异。

**为什么不加锁**：锁需要过期、续租、崩溃回收——那是另一套要长期维护的状态。
而配置只是一份**小文档**，整份覆盖 + 一次版本比对就足以消除静默覆盖。这是
"用最小的机制解决这个具体问题"，而不是"上分布式那一套"。

### 30.3 三个刻意的细节

**冲突用异常，不用返回值。** `set_setup` 抛 `SetupConflict` 而不是返回一个状态。
理由很具体：返回值太容易被忽略——现有调用方就是
`if result is None: 404`，冲突会**悄悄变成 404**。抛异常强迫调用方显式决定。

**清空配置也要 +1。** 不 +1 的话，正在编辑的人（拿着旧版本号）会在"清空"之后
成功保存，把清空这件事悄悄抹掉——那正是这一轮要消除的行为。

**写坏的 `If-Match` 返回 400，不退化成无条件写入。** 解析不出来时返回 `-1`，
调用方转 400。把它当成"没有条件"会把一个写错的头静默降级成覆盖，正好丢掉
这一轮建立的全部保护。

### 30.4 前端：冲突时必须**停止**自动保存

编辑端（`Workbench`）保存时带上 `If-Match`，拿到 200 就把响应里的新版本记下来。
拿到 409 时：

1. 把版本置为"未知"（后续保存不再带 `If-Match`……不，是**先不保存**）；
2. 状态切成 `conflict`，显示"**你的改动没有保存**"并给一个"重新加载"按钮；
3. **自动保存直接 return**——这时候手里的基线是过期的，继续写只会一次次撞
   409，而用户完全不知道发生了什么。

只显示一个红色状态码是不够的：用户会以为改动已经保存了。文案里必须明确
"没有保存"，并说明"重新加载会丢弃本地未保存的改动"。

### 30.5 这一轮我自己的两个错

**写死的版本号。** verify 里第一版写的是 `If-Match: "0"`，而那一节前面已经保存
过几次——于是 `verify` 如实报了 `HTTP Error 409: Conflict`。
**机制本身是对的，错的是我**：真实客户端就该先 GET 读版本再条件保存。改成动态
读版本后全绿，并且这一条恰好成了"409 真的会拦住人"的现场证据。

**给端点加了 `Response` 参数。** 为了在 200 上发 `ETag` 头，我注入了一个
`Response`——结果它挤进位置参数，把"直接调用端点函数"的一批既有测试全弄坏了
（`'Depends' object is not subscriptable`）。改成版本号放**响应体**（客户端本来
就读 JSON），只在 409 上附 `ETag`。端点的位置参数顺序是这个仓库的**事实接口**
（测试直接调端点），动它得有充分理由。

### 30.6 一个观察：跑了二十多轮的 dev 后端死在 16 万单元网格上

verify 有一次在收敛基准（最细一级 164378 个单元）处**后端静默死亡**：日志没有
任何 traceback，客户端拿到 `ConnectionResetError`。重启后同样的 verify 全绿。

我的判断（**未证实**）：那是内存耗尽，与这次改动无关——那个后端进程从很早以前
一直活着，服务过二十多轮 verify（每轮都会划好几个网格、跑若干次求解）。

但它指向一个**真实的设计问题**：`jobs.py` 的任务表按**条数**保留结果，而每条
结果可以很大（例如模态结果带 8 阶振型 × 16 万节点 × 3 分量 ≈ 几十 MB）。
长时间运行时这是只增不减的内存占用。**本轮没有动它**——没有复现就不能说已经
定位，留作下一轮的候选（按体积淘汰，或对老任务只保留摘要）。

### 30.7 验证

- 后端新增 `SetupConcurrencyTest`（13 个用例）：版本递增、无条件写入、过期保存
  **不改动库内容**、冲突报告当前版本、项目不存在不算冲突、清空也 +1、
  `If-Match` 的各种写法与垃圾输入、端点级的 200/409/400。
  全量 **494** 个用例通过。
- verify 新增 5 项（共 **142** 项），全是 HTTP 级的：

## 三十一、第二十八轮：任务结果按体积保留（治一个只增不减的内存）

### 31.1 上一轮留下的线索

上一轮 verify 有一次在收敛基准最细一级（164378 个单元）处让后端**静默死亡**，
日志没有 traceback，重启后同样的 verify 全绿。当时我写的是"判断是内存耗尽，
**未证实**"。

未证实，但顺着它看代码就能看到一个**确定成立**的问题：

```python
MAX_JOBS = 12          # 只按**条数**淘汰
```

而一条结果可以非常大——模态结果是 `mode_shapes`（阶数 × 节点数 × 3 分量），
十几万节点 × 8 阶就是几十 MB。也就是说"最近 12 条结果全留着"最坏是几百 MB，
而且**只增不减**：淘汰只发生在提交新任务时，删掉的是最旧的那条，总量长期维持
在高位。长时间运行的后端迟早在这上面出事。

**这一轮修的是这个确定成立的问题，不是那个未证实的崩溃。** 两者的区别很重要：
前者可以断言、可以测试，后者在没有复现之前只能说"怀疑"。

### 31.2 三条上限，以及它们为什么必须互相自洽

| 常量 | 值 | 作用 |
|---|---|---|
| `MAX_SINGLE_RESULT_BYTES` | 32 MB | 单条超过就**不保留内容**（状态仍是 succeeded） |
| `MAX_RETAINED_RESULT_BYTES` | 64 MB | 所有结果的总体积预算 |
| `MIN_RESULTS_KEPT` | 2 | 无论预算多小，最新 2 条一定保留 |

**这三个数必须自洽**：`单条上限 × 至少保留条数 ≤ 总预算`（32 MB × 2 = 64 MB ✓）。
不满足的话，"总量不超过预算"就是**假的**——两条各自合法的结果就足以超过预算，
而代码还认为自己守住了。所以有一条测试专门断言这个关系，而不是把它留在注释里。

`MIN_RESULTS_KEPT` 的存在理由很实际：轮询是"提交后几秒内取回结果"。如果刚算完的
那条被后面的大结果挤掉，那个客户端会拿到一个空结果——而这个下限让常见路径不受
预算影响。

### 31.3 测量本身不能太贵

要按体积淘汰就得知道体积。而**精确测量要先把结果 `json.dumps` 一遍**——为了知道
"它有多大"而先把内存翻倍，正好和这里的目的相反。

所以用一个**故意不精确**的估算器：递归字典/列表、字符串按 UTF-8 长度、数值按
8 字节，而**大列表只抽样第一个元素外推其余**。实测：

```
8 阶 × 50000 节点 × 3 分量：估算 21.4 MB，耗时 0.0 ms
（真实浮点字节数 9.2 MB —— 估算偏大，对预算而言是安全方向）
```

有一条测试专门用 500 万元素的嵌套数组给它计时，钉住"这个估算不许遍历整个数组"
——否则某天有人"顺手改成精确"就会在 worker 线程上白白烧掉几秒。

### 31.4 结果被丢弃时必须说出来

服务端不保留内容时，前端拿到的 `result` 是 `null`。**如果不做处理，用户看到的是
"求解完成"却是空结果**——他会以为是自己看错了，或者功能坏了。

所以：响应里带 `resultDropped` 与 `resultBytes`，`pollJob` 见到
`resultDropped && result == null` 就抛出一个**准确的**错误：

```
求解已完成，但结果约 70 MB，超过服务端保留上限，未保留。
请减小网格规模（或降低模态阶数）后重试。
```

用抛错而不是静默返回空：走的是既有的错误展示路径，文案能说清原因和下一步。
状态本身仍然是 `succeeded`——事情确实算完了，只是结果没能留下，这两件事不该混。

### 31.5 让占用变成可观测的

`GET /api/jobs` 的 `stats` 里新增：

```
已保留 928378 / 67108864 字节，丢弃 0 条
```

内存问题如果**不可观测**，就只能等它把进程吃掉才发现。这也成了 verify 的一条
检查（写的时候我把字段读成了顶层，检查如实报出"已保留 None / None 字节"——
比"静默通过"好得多）。

### 31.6 验证

- 新增 `ResultRetentionTest`（11 个用例）：估算器随数据增长、对模态形状量级正确、
  **不许遍历整个数组**（计时）、单条超限不保留但状态仍成功、小结果照常保留、
  超预算时回收**最旧**的、`MIN_RESULTS_KEPT` 下限、**单条上限与预算自洽**、
  stats 报出字节数、**运行中的任务绝不回收**。
  全量 **505** 个用例通过。
- verify 新增 1 项（共 **143** 项）：`/api/jobs` 的任务表自省字段。
- `tsc --noEmit`、`vite build` 通过。
