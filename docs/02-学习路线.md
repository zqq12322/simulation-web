## 二、有限元理论（★★★★★，核心中的核心）

**为什么**：你现在能改"代码"，但判断不了"结果"。比如本项目修复后，立方体拉伸的位移是解析解的 0.835 倍——**你必须知道为什么这个偏差是合理的**（全约束端抑制泊松收缩 → 等效变刚），才能确认求解器没错。

**必须掌握**：

1. **弱形式与变分原理**：为什么把微分方程变成积分形式，形函数、试函数、加权残值法；
2. **等参元与数值积分**：高斯积分点、雅可比矩阵、为什么单元不能太畸形；
3. **线弹性有限元推导**：`K = ∫ Bᵀ D B dV`，位移插值 → 应变 → 应力；
4. **收敛性与误差**：h 加密、p 加密、能量范数、应力集中处的奇异性；
5. **常见病**：剪切锁定、体积锁定、沙漏、刚体位移（约束不足导致矩阵奇异）。

**对应本项目代码**：

| 概念 | 代码位置 |
|---|---|
| 弱形式装配刚度阵 | `backend/solver.py` → `asm(linear_elasticity(lam, mu), basis_vec)` |
| 形函数/单元类型 | `ElementVectorH1(ElementTetP1())`（线性四面体） |
| 位移自由度映射 | `basis_vec.nodal_dofs[0/1/2]` |
| 约束施加 | `condense(K, f, D=D)` |
| 刚体位移兜底 | `solver.py` 中"无约束时固定 3 个远端点"的分支 |

**学到什么程度**：能独立推导 `K u = f` 的来源，能解释"网格加密后应力为什么先升后稳"，能判断一个反直觉的结果是物理效应还是 bug。

**资源**：
- 王勖成《有限单元法》（中文，系统全面，适合打底）
- Bathe, *Finite Element Procedures*（工程视角，经典）
- Hughes, *The Finite Element Method: Linear Static and Dynamic Finite Element Analysis*
- **scikit-fem 官方文档与 examples**（`backend/venv/Lib/site-packages/skfem/` 内有源码，直接对照你正在用的库）
- Felippa 的 IFEM 课程笔记（网上免费，推导极清晰）

## 三、弹性力学 / 连续介质力学（★★★★★）

**为什么**：有限元是"工具"，力学是"物理"。不懂力学就会出现"程序跑通了，但我不知道结果对不对"。

**必须掌握**：
1. 应力张量、应变张量、平衡方程、几何方程、本构方程；
2. **主应力与等效应力（Von Mises）的物理意义**——为什么用它判断金属屈服；
3. Lamé 参数与 E、ν 的换算（见 `lame_parameters`）；
4. 应力集中（带孔平板 Kt≈2–3）、圣维南原理（为什么加载方式只影响局部）；
5. 平面应力 vs 平面应变 vs 三维的适用条件。

**对应本项目代码**：
- `backend/solver.py` → `linear_stress(lam, mu)`：σ = 2μ·ε + λ·tr(ε)·I
- `backend/solver.py` → Von Mises 计算：`sqrt(3/2 · s_dev : s_dev)`
- 本项目曾经把 `eye(e, 3)` 写错（应为 `eye(trace(e), 3)`）——**只有懂张量代数才能一眼看出这种错误**。

**资源**：徐芝纶《弹性力学》（中文经典）；Landau & Lifshitz, *Theory of Elasticity*（物理视角，薄而深）。

## 四、数值线性代数与稀疏求解（★★★★☆）

**为什么**：有限元的 90% 时间是解 `K u = f`。网格一大，内存和速度就是瓶颈。

**必须掌握**：
1. 稀疏矩阵存储（CSR/CSC）、组装过程（COO → CSR）；
2. 直接法（Cholesky/LU，如 UMFPACK、MUMPS）vs 迭代法（CG、GMRES）；
3. 预处理（对角、ILU、AMG）、条件数、收敛判据；
4. 对称正定系统的性质（为什么弹性问题用 CG）。

**对应本项目代码**：
- `asm(...)` 返回稀疏矩阵（`scipy.sparse`）
- `solve(*condense(K, f, D=D))` 用的是稀疏直接求解器
- `mass_matrix`/L² 投影也是一次稀疏求解

**学到什么程度**：能判断"该换迭代求解器了"，能读懂 `-ksp_` 类参数，能解释为什么约束不足时求解失败。

**资源**：Trefethen & Bau, *Numerical Linear Algebra*（薄、优美、必读）；scipy.sparse 文档；PETSc 用户手册（了解工业级方案）。

## 五、几何建模与网格生成（★★★★☆）

**为什么**：仿真工程师 60% 的时间花在几何清理和网格上。这个项目现在的边界条件靠"几何猜测"，就是因为没有用好几何拓扑信息。

**必须掌握**：
1. **B-Rep（边界表示）**：面/边/顶点的拓扑关系、参数曲面（u,v 参数域）、法向与参数化边界；
2. **CAD 格式**：STEP（ISO 10303，AP203/AP214）承载 B-Rep，STL 只有三角面片（无拓扑），IGES 更老；
3. **OpenCASCADE (OCCT)** 基本概念（gmsh 内置它）；
4. **Gmsh API**：`getEntities` / `getParametrizationBounds` / `getNormal` / `getMass` / **Physical Groups**；
5. **网格质量指标**：雅可比比、长宽比、扭曲度；Delaunay/前沿推进法；
6. 网格收敛性与局部细化。

**本项目**：`backend/geometry.py` 全部围绕这些；**改错 API 导致所有面法向为 `None`** 就是这一块没学透的直接后果。修复后圆柱面面积 188.5 = 2π·3·10，正好验证了 `getMass` 的正确使用。

**现成的学习材料（已经在你硬盘上！）**：
- `backend/venv/share/doc/gmsh/tutorials/` —— Gmsh 官方 t1–t21 教程（`.geo` + Python 版），从最简单的正方形到复杂工业件
- `backend/venv/share/doc/gmsh/examples/` —— 大量 `geo`/`api` 例子（布尔运算、STL 修复、参数曲面、边界层网格等）
- Gmsh 官方文档 "Gmsh API" 与 "Mesh" 章节

> 建议：花一个下午把 t1–t10 的 Python 版跑一遍，你对网格生成的理解会超过 90% 的同类项目。

## 六、Python 科学计算与工程化（★★★★☆）

**为什么**：这个项目的 Python 代码现在还是"脚本风格"——`print` 调试、没有测试、异常被 `except: pass` 吞掉。

**必须掌握**：
1. **NumPy 向量化**与**广播规则**（本次踩坑：NumPy 2.0 改了 `np.cross` 的轴约定，导致代码静默失效）；
2. `scipy.sparse`、`scipy.linalg`；
3. 依赖管理：venv、`requirements.txt` vs `pyproject.toml`、锁版本；
4. **测试**：`pytest`、`httpx` 测 FastAPI、回归算例（把解析解写成断言）；
5. 异常处理：不要 `except: pass`（本次的"面法向全为 None"就是被它掩盖的）；
6. 类型标注 + 静态检查（`mypy`/`ruff`）。

**对应本项目代码**：`solver.py` 的规范化、`geometry.py` 的 `_normal_from_surface_mesh`、`scripts/verify.ps1` 的雏形。

## 七、Web 前端：React + three.js（★★★☆☆）

**为什么**：这是用户唯一看到的部分。CAE 软件的专业感 80% 来自 3D 交互。

**必须掌握**：
1. **React 19**：函数组件、`useState`/`useEffect`/`useMemo`/`useRef`、受控组件、**副作用依赖数组**（本项目弹窗"重开后显示旧值"就是缺 `useEffect` 同步）；
2. **TypeScript**：`tsc --noEmit`、联合类型、`import.meta.env` 类型声明（本项目缺 `vite-env.d.ts`）；
3. **three.js 核心**：场景/相机/渲染器、几何与材质、`BufferGeometry`、坐标变换；
4. **@react-three/fiber + drei**：声明式 3D、`OrbitControls`、Gizmo；
5. **射线拾取（Raycasting）**：点击选中面/边/点，世界坐标 → 局部坐标（本项目 `Scene3D.tsx` 的 `handleClick`）；
6. **自定义着色器（GLSL）**：把标量场映射成彩虹云图（本项目 `SimulationResultShader`）；
7. 性能：`useMemo` 缓存几何、大网格用 instancing / WebWorker。

**资源**：React 官方文档（新版教程质量很高）；three.js manual + examples；drei 文档；《WebGL 编程指南》（打底图形学）。

## 八、后端服务与云部署（★★★☆☆）

**必须掌握**：
1. **FastAPI**：路由、Pydantic 模型、依赖注入、CORS、静态文件、`/docs` 自动文档；
2. **异步与长任务**：为什么网格/求解不能放在同步 HTTP 请求里（本项目现在就是，大件会超时）→ Celery/RQ/Redis 或 BackgroundTasks + 轮询/WebSocket；
3. **数据库**：SQLite → Postgres，ORM（SQLAlchemy/Supabase）；
4. **Docker**：镜像分层、把 gmsh 的系统依赖装进镜像；
5. **部署现实**：Serverless（Vercel）不适合跑重型原生计算——本项目 `vercel.json` 想把 gmsh 放上去，实际很可能超时/超限，应改为常驻容器；
6. **安全**：密钥管理（`.env`，永不入库）、文件上传校验（防路径穿越）、CORS 白名单、鉴权。

## 九、CAE 后处理与可视化规范（★★☆☆☆）

**为什么**：同样是云图，"看起来专业"和"看起来像学生作业"差在细节。

- 图例必须带**单位与量级**（本项目图例写的是 MPa，但内部数值实际是"Gmsh 单位"，这是个 bug 级的不一致）；
- 色标规范（彩虹色并不总是最佳，感知均匀色标如 viridis 更严谨）；
- 变形放大系数要**显式标注**（本项目算了 `deformationScale` 但着色器里未真正应用位移）；
- 剖切面、等值面、探针取值、时间/载荷步动画、报告导出（PNG/CSV/VTK/PDF）。

**参考**：ParaView 的使用习惯就是行业事实标准，照着它的功能列表做，方向不会错。

## 十、LLM 应用工程（★★☆☆☆，但最能做出亮点）

**现状**：本项目 AI 助手只是"聊天 + 关键词路由 + 解析 JSON"，属于玩具级。

**要学**：
1. **结构化输出 / Function Calling**：让模型直接产出符合 JSON Schema 的仿真配置，再由后端**校验合法性**（材料 ID 是否存在、面 ID 是否真实存在、载荷是否超限）；
2. **不要让 LLM 直接算数**：它只负责"生成配置"，数值正确性必须由 FEM 求解器保证；
3. **诊断闭环**：求解失败 → 把真实报错 + 上下文喂给模型 → 给出可执行的修改建议（本项目已实现雏形，见 `ai_assistant.py` 的 `/diagnose` 与 `Workbench` 中失败自动唤起诊断）；
4. RAG：把 Gmsh/scikit-fem 文档切片入库，让助手回答"这个选项什么意思"。

## 十二、建议的学习节奏

**8 周速成路线（配合阶段 1–2 开发）**

| 周 | 学 | 同步做 |
|---|---|---|
| 1 | 弹性力学：应力/应变/本构 + 等效应力 | 给求解器写立方体拉伸回归测试 |
| 2 | 有限元：弱形式 → K u = f 推导 | 读 `skfem` 源码对应自己的 `solver.py` |
| 3 | 稀疏线性代数 + 收敛性 | 做网格加密收敛性实验，出曲线 |
| 4 | Gmsh API + Physical Groups | 用物理组重写边界条件绑定 |
| 5 | 面力积分（形函数积分） | 实现真实压力载荷，与 p×A 对照 |
| 6 | pytest + 工程化 | 3 个标准算例入 CI |
| 7 | React 状态管理 + three.js 拾取 | 重构 Workbench 状态、改进拾取 |
| 8 | 异步任务 + Docker | 网格/求解异步化 + 进度条 |

**长期心态**：仿真软件的门槛在"物理 + 数值"，不在"框架"。框架三个月能学会，物理和数值要吃三年。
**所以把 70% 的精力放在第二、三、四、五节，前端够用就行。**
